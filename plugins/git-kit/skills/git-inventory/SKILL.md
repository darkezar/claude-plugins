# Инвентаризация состояния репозитория

Снимок делается **до** любых выводов и правок. Ниже — команды и то, как читать их вывод.
Почти каждая имеет ловушку, из-за которой её ответ понимают неправильно.

Всё read-only. Ничего из этого файла не меняет репозиторий.

## Шаг 0. Это вообще репозиторий?

```bash
git rev-parse --is-inside-work-tree 2>/dev/null || echo "не репозиторий"
git rev-parse --show-toplevel
```

Если нет — дальше идти некуда, так и скажи. Каталог может быть подкаталогом чужого
репозитория: `--show-toplevel` покажет настоящий корень, и он может оказаться не там,
где ожидалось.

## Шаг 1. Где HEAD

```bash
git branch --show-current          # пусто → detached HEAD
git log -1 --format='%h %s (%cr)'
```

**Ловушка:** пустой вывод первой команды — это не ошибка, это `detached HEAD`. Коммиты,
сделанные в таком состоянии, не принадлежат ни одной ветке и исчезнут после переключения,
оставшись только в reflog. Это первый по важности случай во всём файле.

Отдельно: **ветка меняется между сессиями.** Тот, кто работает без git-интерфейса, обычно
уверен, что стоит там же, где был вчера. Всегда показывай текущую ветку явно, даже когда
всё в порядке.

## Шаг 2. Незавершённая операция

```bash
git status --short --branch
ls .git/MERGE_HEAD .git/CHERRY_PICK_HEAD .git/REVERT_HEAD .git/BISECT_LOG 2>/dev/null
ls -d .git/rebase-merge .git/rebase-apply 2>/dev/null
```

Наличие любого из этих путей означает, что репозиторий **застрял посреди операции**:
rebase, merge, cherry-pick, revert или bisect. Пока она не завершена, ветка находится
в промежуточном состоянии, часть коммитов может быть не на месте, а `git status` показывает
конфликты как обычные изменения.

Это состояние надо распознать **до** всего остального: советовать коммит или переключение
ветки, пока идёт rebase, — вредно.

## Шаг 3. Незакоммиченное

```bash
git status --porcelain=v2 --branch --untracked-files=normal
git diff --stat                    # рабочее дерево против индекса
git diff --cached --stat           # индекс против HEAD
```

Три разных множества, которые постоянно путают:

| Что | Как увидеть | Риск |
|---|---|---|
| Изменённое, не добавленное | `git diff` | Есть только на диске |
| Добавленное в индекс, не закоммиченное | `git diff --cached` | Есть только на диске |
| Неотслеживаемые файлы | `git status` → `?` | Есть только на диске, и в дифф не попадают вообще |

**Ловушка:** неотслеживаемый файл невидим для `git diff` и для всех ревью-инструментов.
Новый файл, который забыли добавить, — типовая потеря: работа сделана, а в PR её нет.

Отдельно посмотри, нет ли среди неотслеживаемых того, чего в репозитории быть **не должно**:
`.env`, ключи, дампы, архивы. Не предлагай их коммитить — предложи `.gitignore`.

## Шаг 4. Что существует только на этом диске

Главный вопрос всего файла: **что исчезнет, если диск умрёт прямо сейчас.**

```bash
git for-each-ref --format='%(refname:short) | up=%(upstream:short) | track=%(upstream:track) | %(committerdate:relative) | %(committerdate:unix)' refs/heads
```

Как читать `track`:

| Значение | Что это значит |
|---|---|
| пусто, и `up` заполнен | ветка совпадает с origin — в безопасности |
| `[ahead N]` | N коммитов есть только здесь |
| `[behind N]` | отстала от origin, но ничего своего не теряет |
| `[ahead N, behind M]` | разошлись, при слиянии будет rebase или merge |
| `[gone]` | ветка на origin **удалена** — почти всегда PR слит и ветка подчищена |
| `up` пустой | upstream нет вообще: ветку **никогда не пушили** |

Последние две строки — самые содержательные. `up` пустой означает, что все коммиты ветки
существуют в единственном экземпляре. `[gone]` — наоборот, кандидат на удаление.

## Шаг 5. Слитые ветки

```bash
git branch --merged <base>
git branch --no-merged <base>
```

**Ловушка, из-за которой этот шаг чаще всего врёт:** `--merged` понимает только настоящее
слияние. Если в проекте включён **squash merge** (по умолчанию у многих репозиториев на
GitHub), слитая ветка останется в `--no-merged` навсегда, потому что её коммитов в базе нет —
там один новый коммит с их содержимым.

Надёжная проверка, работающая при обоих способах:

```bash
git cherry <base> <branch>
```

Строки с `-` — коммиты, содержимое которых **уже есть** в базе. Строки с `+` — которых нет.
Ни одного `+` → ветка фактически слита, чем бы её ни сливали.

Базовую ветку не хардкодь:

```bash
BASE=$(git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null | sed 's|^origin/||')
[ -z "$BASE" ] && for b in main master develop trunk; do git show-ref --verify --quiet "refs/heads/$b" && BASE=$b && break; done
```

## Шаг 6. Стеши

```bash
git stash list --format='%gd | %ci | %gs'
git stash show --stat 'stash@{0}'        # по каждому: что внутри
```

Сообщение стеша (`%gs`) содержит ветку, на которой он был сделан: `WIP on <ветка>: ...`.
Это важнее даты — стеш, снятый с давно слитой ветки, скорее всего уже не нужен, а стеш
с живой ветки может оказаться незаконченной работой.

**Ловушка:** стеш не принадлежит ветке и не виден нигде, кроме `git stash list`. О нём
забывают полностью. При этом он содержит незакоммиченную работу — то есть относится
к самой рискованной категории.

Никогда не суди о содержимом стеша по его имени. Только по `git stash show`.

## Шаг 7. Worktrees

```bash
git worktree list
```

Строк больше одной — есть дополнительные рабочие каталоги. В каждом своя ветка и своё
незакоммиченное состояние, невидимое из основного каталога:

```bash
git -C <путь-worktree> status --short --branch
```

Строка с пометкой `prunable` означает, что каталог удалён, а запись осталась.

## Шаг 8. Открытые PR (если доступен gh)

Необязательный шаг: он превращает «ветка непонятного назначения» в «ветка ждёт ревью».

```bash
command -v gh >/dev/null || export PATH="$HOME/.local/bin:$HOME/bin:$PATH"
gh pr list --state open --json number,headRefName,title,isDraft,reviewDecision 2>/dev/null
```

`gh` часто установлен вне `PATH` — прежде чем считать его отсутствующим, проверь
`~/.local/bin` и `~/bin`. Нет авторизации или нет сети — пропусти шаг и скажи об этом
одной строкой, не выдумывая статусы PR.

## Что вернуть

Структурированный факт-лист, без выводов и советов — их делает вызывающая команда:

- текущая ветка (или detached), последний коммит, идёт ли незавершённая операция;
- базовая ветка и как она определена;
- незакоммиченное: изменённое / в индексе / неотслеживаемое, с количеством файлов;
- по каждой ветке: upstream, track, возраст, слита ли по `git cherry`, есть ли открытый PR;
- стеши: сколько, возраст каждого, исходная ветка, размер;
- worktrees: пути, ветки, чистота;
- что проверить не удалось и почему.
