# Детект тулинга проекта

Задача — не «знать, как принято в Laravel», а **выяснить, как сделано здесь**. Одно и то же
намерение в соседних репозиториях называется по-разному и запускается по-разному.

## Шаг 1. Найди точку входа

Порядок предпочтения — сверху вниз. Нашёл на уровне выше — ниже не спускайся: обёртка обычно
знает про окружение то, чего не знает голый бинарь.

| Приоритет | Источник | Как смотреть |
|---|---|---|
| 1 | `Makefile`, `justfile`, `Taskfile.yml` | цели и их тела |
| 2 | `composer.json` → `scripts`, `package.json` → `scripts` | имена скриптов |
| 3 | Прямые бинари | `vendor/bin/*`, `node_modules/.bin/*`, `artisan` |

```bash
ls Makefile makefile justfile Taskfile.yml 2>/dev/null
grep -nE '^[a-zA-Z0-9_-]+:' Makefile 2>/dev/null | head -40
python3 -c "import json;print(list((json.load(open('package.json')).get('scripts') or {}).keys()))" 2>/dev/null
python3 -c "import json;print(list((json.load(open('composer.json')).get('scripts') or {}).keys()))" 2>/dev/null
```

**Читай тело цели, а не только имя.** Имя говорит о намерении, тело — о способе запуска.

```bash
grep -A3 '^test:' Makefile
grep -E '^[A-Z_]+ *[:?]?=' Makefile   # переменные вроде DC := docker compose -f ...
```

**Разворачивай переменные — они бывают вложенными.** Тело цели редко содержит команду целиком:
чаще там `$(APP) php artisan test`, где `APP := $(COMPOSE) run --rm --no-deps app`, а `COMPOSE`
объявлен ещё выше. Пока не раскрутишь цепочку до конца, ты не знаешь ни про контейнер, ни про
флаги. Признак контейнера — `docker compose`, `docker exec`, `sail` в **развёрнутом** виде,
а не в исходной строке цели.

Обрати внимание и на форму запуска: `run --rm` поднимает новый одноразовый контейнер (работает,
даже когда окружение не поднято), а `exec` требует уже запущенного сервиса. Это разные требования
к состоянию окружения.

## Шаг 2. Сопоставь намерения

Одно намерение — много имён. Сопоставляй по смыслу, а не по точному совпадению.

| Намерение | Встречающиеся имена целей |
|---|---|
| тесты | `test`, `tests`, `phpunit`, `pest`, `check` |
| линтер | `lint`, `lint-all`, `pint`, `pint-check`, `phpcs`, `front-lint`, `web-lint`, `eslint` |
| типы | `typecheck`, `types`, `front-typecheck`, `web-types`, `tsc`, `stan`, `phpstan` |
| формат | `fmt`, `fmt-check`, `format`, `pint` (без `--test` — правит файлы!) |

**Различай проверку и правку.** `pint` правит файлы, `pint --test` и `pint-check` только проверяют.
Для ревью нужна проверяющая форма — правящую не запускай без явной просьбы.

## Шаг 3. Учти окружение

**Контейнер.** Если тело цели содержит `docker compose exec` / `docker exec` / `sail`, команда
идёт внутрь контейнера, и на хосте нужного бинаря может не быть вовсе.

- Контейнер должен быть поднят. Проверь: `docker compose -f <файл> ps`. Если сервис не запущен —
  скажи об этом прямо и предложи `make up`, а не пытайся запускать интерпретатор на хосте.
- Нет прав на docker-сокет (`permission denied /var/run/docker.sock`) — тоже сообщай честно.
  Не подменяй прогон статическим разбором молча.
- **Добавляй `-T`**, если его нет в цели: без TTY `docker compose exec` в неинтерактивном
  вызове падает или виснет. `docker compose exec -T app ...`.

**Sail.** `./vendor/bin/sail` — та же обёртка над compose; цели вида `sail-up` поднимают окружение.

**Монорепо.** Бэкенд часто идёт через контейнер, а фронтенд — напрямую на хосте
(`npm --prefix web run lint`). Это **разные** команды для разных частей диффа: выбирай ту,
которая соответствует затронутым файлам, а не запускай обе подряд.

**Диффо-ориентированные цели.** Цель может линтовать не весь проект, а только изменённые файлы
относительно базовой ветки — и с разной строгостью для новых и правленых. Такую цель вызывай
как есть, не переписывай на прямой вызов линтера: логика отбора файлов в ней и есть ценность.

## Шаг 4. Верни карту

```
Точка входа: Makefile | npm scripts | прямые бинари | не найдено
Окружение:   хост | docker compose (файл, сервис) | sail

тесты:   <команда>  | не настроено
линтер:  <команда>  | не настроено
типы:    <команда>  | не настроено
формат:  <команда>  | не настроено

Рабочий каталог: <откуда запускать>
Ограничения: <контейнер не поднят / нет доступа к docker / бинаря нет на хосте>
```

## Правила

- **Не выдумывай результат прогона.** Если запустить нельзя — напиши почему и что для этого нужно.
  Формулировка «тесты прошли» без фактического запуска недопустима.
- **Не изобретай команду, если есть цель.** `make test` лучше, чем собранный вручную
  `docker compose exec ... php artisan test`: в цели могут быть переменные окружения, флаги
  и подготовка базы.
- **Не запускай правящие команды** (форматирование, автофиксы, миграции) в рамках проверки.
- Инструмент **не настроен** — это нормальный, честный ответ. Многие проекты живут без статанализа.
