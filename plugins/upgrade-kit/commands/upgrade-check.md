# Upgrade Check

Составь отчёт о состоянии зависимостей и план обновления.

## Что эта команда делает и чего не делает

**Делает:** инвентаризацию, оценку риска, порядок шагов и список того, что придётся проверить руками.

**Не делает:** не обновляет, не правит код, не обещает, что после обновления всё заработает.
Гарантию даёт прогон тестов и твои руки, а не отчёт. Если тестов в проекте мало, так и скажи
в отчёте: это меняет цену каждого шага.

## Шаг 1. Инвентаризация

Определи стек скиллом `detect-stack` — в монорепо частей несколько, и у каждой свои зависимости.

Прочитай манифесты и **лок-файлы**: манифест говорит о допустимом диапазоне, лок — о том,
что стоит фактически. Расходятся они постоянно.

```bash
composer outdated --direct 2>/dev/null
npm outdated 2>/dev/null
```

Если команды недоступны (нет php, нет доступа к контейнеру) — возьми версии из лок-файлов
и сверь с публичными реестрами, но пометь, что данные из манифеста, а не из живого окружения.

## Шаг 2. Раздели по типу

| Категория | Что это | Риск |
|---|---|---|
| **Без поддержки** | версия больше не получает исправлений безопасности | Высокий, но обновлять надо — это не «на потом» |
| **Патч** | исправления в рамках минорной | Низкий |
| **Минор** | новое, обратно совместимое | Низкий, но проверить объявленные депрекейты |
| **Мажор** | ломающие изменения | Высокий, только по одному за раз |
| **Транзитивные** | подтянуты другими пакетами | Обновлять напрямую нельзя, только через родителя |

Отдельно отметь **фреймворк**: его мажор тянет за собой экосистему, и это всегда отдельная работа,
а не строка в списке.

## Шаг 3. Спроецируй ломающие изменения на **этот** код

Самое ценное. Общий список breaking changes бесполезен — важно, какие из них задевают тебя.

По каждому мажору: прочитай официальный гайд обновления, выпиши ломающие изменения и по каждому
проверь грепом, используется ли затронутый API здесь.

```bash
grep -rn '<удалённый или изменённый API>' --include='*.php' --include='*.ts' . | head
```

Результат по каждому пункту — один из трёх:

- **задевает** — где именно, сколько мест;
- **не задевает** — этот API в проекте не используется;
- **не проверить грепом** — динамические вызовы, магия фреймворка, поведение во время выполнения.
  Так и напиши: это кандидат в ручную проверку.

Не выдумывай содержание гайдов. Гайд недоступен — скажи, а не пересказывай по памяти:
версии выходят чаще, чем обновляется память.

## Шаг 4. Порядок

Составь план шагами, каждый — отдельный коммит и отдельная проверка:

1. **Сначала безопасность** — версии без поддержки и известные уязвимости, даже если это мажор.
2. **Потом дешёвое** — патчи и миноры пачкой: если тесты зелёные, риск мал.
3. **Потом мажоры по одному.** Два мажора в одном коммите — гарантия того, что при поломке
   не поймёшь, который виноват.
4. **Фреймворк — отдельно от всего.**

По каждому шагу укажи: что обновляем, что проверить автоматически, **что проверить руками**
(сценарии, которые тесты не покрывают), и как откатиться.

## Отчёт

```
## Состояние зависимостей

Части проекта: <какие> | Данные: из окружения / из лок-файлов

### Без поддержки — обновлять в первую очередь
- `пакет` текущая → рекомендуемая. Чем грозит: ...

### Мажоры
- `пакет` X → Y
  Задевает: file:line (N мест) — <какое изменение>
  Не задевает: <перечислить проверенное>
  Не проверить статически: <что смотреть руками>

### Миноры и патчи
- перечислить кратко, одной пачкой

### Транзитивные
- `пакет` — тянется через `родитель`, обновится вместе с ним

## План

Шаг 1. <что> — проверить: <тесты> — руками: <сценарии> — откат: <как>
Шаг 2. ...

## Оговорки
- Тестовое покрытие: <оценка> — чем оно меньше, тем дороже каждый шаг
- Гайды, которые не удалось прочитать: <какие>
```

После каждого шага логично прогнать `/agent-full-review` — обновление часто меняет поведение
незаметно, а ревью видит дифф целиком.
