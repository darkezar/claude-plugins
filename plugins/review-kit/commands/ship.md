# Ship: Commit + Push + PR

Выполни полный цикл отправки кода. Строго следуй каждому шагу.

## Шаг 0. Контекст проекта

Определи базовую ветку и активные стеки по скиллу `detect-stack`. Из картриджей стека возьми
команды проверок для Шага 3 — не угадывай их и не вызывай наугад.

Прочитай `CLAUDE.md` / `AGENTS.md` проекта: там могут быть заданы префикс веток, шаблон коммитов,
дополнительные проверки и список файлов, запрещённых к коммиту.

## Шаг 1. Проверка ветки

```bash
git branch --show-current
```

**Если текущая ветка совпадает с базовой (`main`/`master`/`develop`) — СТОП.**

- Коммитить в базовую ветку строго запрещено.
- Спроси у пользователя название фичи или задачи.
- Создай ветку с префиксом `darkezar/` (или тем, что задан в `CLAUDE.md` проекта):
  `git checkout -b darkezar/<название>`

## Шаг 2. Контекст изменений

```bash
git status
git diff
git diff --cached
git log --oneline -5
```

Определи суть изменений и есть ли merge-коммит из базовой ветки (на случай конфликтов).

## Шаг 3. Проверки перед коммитом

Прогони типы и линтер — не коммить заведомо красное. Команды бери из картриджа стека и
запускай из правильного каталога (в монорепо — из каталога соответствующего приложения).

Перед запуском убедись, что скрипт или бинарь реально существует (`package.json`,
`composer.json`, `vendor/bin`). Несуществующую команду не вызывай.

Если есть ошибки — почини их или явно предупреди пользователя перед коммитом.

## Шаг 4. Stage и Commit

Сформируй осмысленное сообщение коммита:

- на английском;
- краткий title до 70 символов — что сделано и зачем;
- если изменений много — добавь body с деталями;
- префиксы по смыслу: `feat:`, `fix:`, `refactor:`, `style:`, `chore:`.

```bash
git add <конкретные файлы>
git commit -m "сообщение"
```

**`--no-verify`** без явной причины не использовать. Флаг нужен, только когда в проекте есть
pre-commit хуки и их требуется осознанно пропустить — например после merge базовой ветки
с массовыми авто-правками форматирования. Если хуков нет, флаг не нужен вовсе.

## Шаг 5. Push

```bash
git push -u origin $(git branch --show-current)
```

Если remote-ветки нет — push создаст её с флагом `-u`.

## Шаг 6. Pull Request

1. Проанализируй **все** коммиты ветки: `git log "$BASE"..HEAD --oneline`
2. Посмотри полный дифф: `git diff "$BASE"...HEAD`
3. Сформируй краткое и человекопонятное описание по шаблону.

```bash
gh pr create --title "$(git branch --show-current)" --body "$(cat <<'EOF'
## Что делает
Одно-два предложения: какую задачу пользователя решает PR. Без технических подробностей.

## Почему
Одно-два предложения: зачем это нужно. Если без контекста не понять — упомяни связанную задачу.

## Что сделано
Один короткий абзац или 2–4 буллета. Суть решения, без пересказа каждой строки диффа.

## Как проверить
1. Конкретный сценарий: куда зайти, что нажать.
2. Что должно произойти — ожидаемое поведение.

## Файлы
- `путь/к/модулю` — одно слово о роли в PR
- (косметика и стили — отдельной строкой, если есть)

🤖 Generated with [Claude Code](https://claude.ai/claude-code)
EOF
)"
```

### Правила описания PR

- **Title** — название ветки как есть.
- **Body на русском**, кратко и человекопонятно, ориентир 30–60 строк.
- **Пиши для человека, а не для лога**: ревьюер за 30 секунд понимает, что и зачем.
- **Без воды**: не пересказывай commit-сообщения и не описывай каждый файл построчно.
- **Не вкладывай буллеты в буллеты** — максимум один уровень.
- **Не вставляй большие куски кода** — имена модулей и пути да, многострочные блоки нет.
- Косметику и стили упоминай одной строкой в «Файлы».
- Связанную задачу — одной строкой в «Почему».
- Если затронут UI — упомяни, что проверено соответствие дизайн-системе проекта.

## Важно

- **Никогда не коммить в базовую ветку** — всегда создавай отдельную.
- **Не делай `git add .` / `git add -A`** — добавляй конкретные файлы.
- **Не коммить секреты**: `.env`, `credentials*`, `*.pem`, `*.p8`, `*.p12`, `*.key`, keystore,
  сервис-аккаунты, локальные настройки инструментов. Плюс то, что перечислено в `CLAUDE.md` проекта.
- **Не коммить артефакты сборки и зависимости**: `node_modules`, `vendor`, `dist`, `build`,
  нативные каталоги, сгенерированные файлы.
- Если PR для этой ветки уже существует — **обнови его**, а не создавай новый.
