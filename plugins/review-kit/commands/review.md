# Code Review

Проведи ревью изменений текущей ветки самостоятельно, одним проходом. Это лёгкая альтернатива
скиллу `agent-full-review`: без параллельных агентов, быстрее и дешевле, но и менее глубоко.
Для полноценного ревью перед PR используй `agent-full-review`.

Работай как строгий, но конструктивный ревьюер. **Отвечай на русском.**

## Шаг 1. Контекст

Определи базовую ветку и активные стеки по скиллу `detect-stack`, затем прочитай картриджи —
в них команды проверок и привязки чек-листа под конкретный стек.

Прочитай `CLAUDE.md` / `AGENTS.md` проекта: доменные правила имеют приоритет над общими
рекомендациями.

## Шаг 2. Scope

```bash
git diff "$BASE"...HEAD --name-only
```

Если ветка не отличается от базы — проверь незакоммиченное: `git diff --name-only`
и `git diff --cached --name-only`.

Прочитай каждый изменённый файл **целиком**, а не только дифф — важен контекст. Определи,
какие части проекта затронуты: от этого зависит, какие разделы чек-листа применять.

## Шаг 3. Прогон инструментов

Команды бери из картриджа стека. Перед запуском убедись, что инструмент реально настроен;
если нет — так и напиши, не выдумывай результат. Приложи итог (passed / N ошибок) к отчёту.

## Шаг 4. Чек-лист

Пройди по разделам, применимым к затронутым файлам.

**Корректность и качество**
- Типизация: строгий режим соблюдён, нет `any`/эквивалента и подавления ошибок без обоснования
- Ошибки обработаны, а не проглочены; предусмотрены пустое состояние, загрузка, отказ
- Ресурсы освобождаются: подписки, таймеры, соединения
- Именование осмысленное; ранние `return` вместо глубокой вложенности
- Нет мёртвого кода, закомментированных блоков и отладочных вызовов
- На новое поведение есть тест; на исправленный баг — тест, падающий без фикса

**Безопасность**
- Нет секретов в коде и в диффе; ничего лишнего не уехало в клиентский бандл
- Ввод валидируется; нет конкатенации ввода в запросы и команды
- Сервер не принимает от клиента то, что обязан вычислить сам (суммы, роли, статусы, владельца)
- В ответах нет чувствительных полей; в логах нет токенов и PII

**Доступ**
- Новые эндпоинты защищены; проверяется не только «залогинен», но и «имеет право»
- Ресурс по идентификатору скоупится по владельцу (IDOR)
- Токены хранятся в подходящем для платформы хранилище; logout отзывает токен на сервере
- Клиентский гейт не выдаётся за защиту

**Производительность**
- Нет N+1 и непагинированных выборок; индексы на горячих колонках
- Нет лишних ре-рендеров и тяжёлых вычислений в рендере; длинные списки виртуализированы
- Нет водопадов запросов и поллинга там, где уместен push

**Дизайн-система** (если затронута вёрстка)
- Цвета и отступы из токенов, не хардкодом; переиспользуются общие UI-примитивы
- Пользовательский текст через словари локализации, ключи во всех локалях
- Деньги и даты через общие хелперы форматирования

## Формат вывода

Для каждого замечания:

```
### [Критичность] Файл:строка — Краткое описание

**Проблема:** что не так
**Решение:** что нужно сделать
```

Критичности:

- **CRITICAL** — баги, уязвимости, обходимая защита, потеря данных
- **WARNING** — нарушение правил проекта, плохие практики, проблемы производительности
- **SUGGESTION** — улучшения, рефакторинг, стиль

В конце — общая оценка:

- краткое резюме в 1–2 предложения;
- результат прогона инструментов: passed или количество ошибок;
- количество замечаний по критичности;
- готовность к мержу: да / да с замечаниями / нет, нужны исправления.
