# Область исправлений и вопросы пользователю

Общая политика `apply-fixes`/`agent-full-review --fix` и `agent-fixer` для Claude и Codex.
Вызов исправлений разрешает обработать **все готовые замечания** в запрошенной области:
блокирующие, важные, механические, мелкие, предложения, упрощения и необязательные
оптимизации. Дополнительное «включая предложения» не требуется. Статус optional/nice-to-have
определяет важность для мержа, но не исключает пункт из применения.

## Что входит в работу

- Возьми полный отчёт: `findings`, все его секции и связанные комментарии PR. `open`
  содержит только важные замечания и не заменяет этот список. Старое автоматическое
  «Отложено по умолчанию» также включается в исправления.
- Явные ограничения пользователя приоритетны: выбранные категории/пункты, «только
  механическое», конкретное решение или явное «это отложить». Не возвращай в работу то,
  что пользователь осознанно исключил. Автоматическая метка старого навыка не равна
  решению пользователя отложить.
- Сверь каждую находку с текущим кодом и контрактами. Исправляй её минимальным достаточным
  изменением, включая необходимые связанные файлы и тесты. Не запускай поиск новых проблем
  и попутный рефакторинг всего проекта.
  При смене имени, API, схемы или общего поведения проверь затронутых вызывающих и
  потребителей, в том числе неизменённые файлы; исправление не ограничивается строкой находки.
- Однозначные исправления логики, авторизации, безопасности, архитектуры, схемы,
  зависимостей и необязательных предложений разрешены так же, как механические.
  Категория, приоритет и размер diff сами по себе не требуют вопроса.

## Когда нужен выбор

Задавай вопрос, только если после чтения кода, правил и уже заданных решений остаются
существенно разные допустимые результаты: поведение, права, публичный контракт, данные,
совместимость или значимый архитектурный компромисс. Не угадывай недостающую продуктовую
семантику. Такое возможно и для необязательного предложения — не отбрасывай его молча.

Обычные детали реализации выбирай сам по существующим соглашениям проекта. Наличие двух
способов написать эквивалентный код, сложность правки или её принадлежность к безопасности
не создают неоднозначности автоматически. Если решение уже дано пользователем или явно
следует из контракта/тестов, реализуй его без повторного подтверждения.

Для вопроса подготовь проблему, конкретный сценарий, существенно различающиеся варианты
с последствиями и рекомендацию. Спрашивает координатор; fixer возвращает недостающий выбор.
Пока выбор не получен, не применяй зависимые от него изменения. Независимые однозначные
пункты продолжай выполнять. Не проси одобрить весь список перед началом исправлений.

## Полнота и подтверждение

Одна проблема может соответствовать нескольким исходным комментариям: исправление делай
один раз, сохрани все comment ID для ответов. В финале каждый пункт полного списка имеет
результат: исправлено / уже исправлено / нужно решение / явно исключено пользователем /
неприменимо с доказательством / не удалось выполнить с конкретной причиной.
Не скрывай необязательные пункты за счётчиком или общей строкой «отложено».

Если находка устарела, уже закрыта или предложенная правка противоречит действующему
контракту, объясни это по текущему коду. Не вноси заведомо неверное изменение ради отметки.
Отсутствующую среду/зависимость обозначь ограничением проверки; это не основание спрашивать
заново, можно ли вообще применять уже разрешённую однозначную правку.

Изменённое поведение проверяй релевантными тестами. Для исправления воспроизводимого дефекта
покажи, что регрессионный тест падает до правки и проходит после, когда это выполнимо.
Если такой прогон недоступен, сохрани причину и границы доказанного. Для механики и
эквивалентного упрощения достаточно подходящих существующих проверок; не пиши тесты,
повторяющие реализацию. Назначай одного исполнителя проверок, повторяй затронутые наборы.

Модель/effort выбирай по [execution-routing.md](execution-routing.md): сложность усиливает
исполнение, а не превращается в формальный запрос разрешения. Один писатель, без дублей
тестов и новых кругов ревью ради косметики. Коммит, push, публикация новых находок и запуск
меняющих среду команд определяются отдельными инструкциями и реальным запросом; разрешение
редактировать код само по себе их не добавляет. Ответы/resolve — по
[fix-review-threads.md](fix-review-threads.md), после подтверждения результата.
