Примени все готовые замечания в запрошенной области по
[общей политике исправлений](../../references/fix-scope.md). Она также действует для `--fix`.

## 1. Источник и состояние

Нужен готовый отчёт либо inline-замечания указанного PR. Если источника нет, сообщи,
что требуется отчёт/PR; новое полное ревью эта команда не проводит.
Прочитай применимые инструкции, проверь ветку/коммит и `git status --short`.
Работай в проверенном worktree, сохраняй правки пользователя и его индекс. Наличие
незакоммиченного само по себе не требует остановки. Неразделимое пересечение с чужими
правками требует уточнения намерения, а не их перезаписи.

Для PR прочитай [ответы и resolve](../../references/fix-review-threads.md) и сохрани
соответствие находок всем исходным комментариям/threads до начала исправлений.

## 2. Полный список

Возьми все находки, включая предложения и старое автоматическое «Отложено по умолчанию».
Соблюдай явно заданные пользователем исключения, категории и принятые решения.
Сверь актуальность и раздели работу на однозначные пункты и действительно требующие выбора.
Категории «безопасность», «логика», «архитектура» и «необязательное» не требуют вопроса сами
по себе. Не проси подтвердить список; начинай независимые однозначные исправления.

## 3. Последовательное применение

Перед каждой партией выбери модель и effort по
[общей политике исполнения](../../references/execution-routing.md), разделы «Решение по
задаче», «Claude Code» и «Отчёт». Передай настройки параметрами Agent tool, если доступны.
Однозначная сложная правка может требовать сильнее модель/effort, но не нового разрешения.

Запусти одного `agent-fixer`, последовательно. Передай все однозначные замечания партии,
включая предложения, уже принятые решения, базовую ветку, картриджи, правила, состояние
дерева, команды проверок и все связанные comment ID. Параллельных писателей не запускай.
Локализацию выполняй через `i18n-sync` в пределах замечаний; переводы не выдумывай.
Fixer возвращает результат каждого пункта и вопросы с вариантами; публикации ведёшь ты.
Если делегация недоступна или запрещена запросом, выполни тот же список самостоятельно
только на допустимой модели/effort по общей политике; иначе сообщи ограничение исполнения.

## 4. Только неоднозначные решения

После изучения кода и правил вопрос нужен лишь для существенно разных допустимых
результатов по [общей политике](../../references/fix-scope.md). Обычные технические детали
выбирай сам по проектным соглашениям; заданное решение повторно не согласовывай.

Подготовь проблему и конкретный сценарий, варианты с последствиями/проверками и рекомендацию.
Спрашивай из основной сессии, дождись недостающего выбора перед зависимыми изменениями.
Независимые пункты продолжай. Необязательное неоднозначное предложение тоже вынеси на выбор,
не откладывай автоматически. После ответа передай fixer выбранное решение, заново оценив
сложность исполнения. Не меняй выбранное поведение без основания и уточнения.

## 5. Проверки

Назначь одного ответственного, команды возьми из инструкций/конфигурации проекта или
`detect-tooling`, если он доступен. Повторяй затронутые тесты, линт и типы, а не весь набор
по привычке. Для воспроизводимого дефекта поведения подтверди регрессионный тест до/после,
когда это выполнимо; ограничения укажи явно. Для механики отдельные тесты не нужны, если
подходящие существующие проверки достаточны. Просмотри полный diff и `git diff --check`.

## 6. Ответы в PR и resolve

Выполни [общую процедуру](../../references/fix-review-threads.md): ответь на каждый inline,
по которому сделана правка, включая частичные исправления и дубли у разных ревьюеров.
Локальное/частичное состояние обозначь честно. Закрывай только целиком решённые в
опубликованном PR threads после проверки актуальных сообщений, головы, прав и `isResolved`.
Сверь весь `reply_map`. `--comment` не требуется; запрет GitHub-действий сохраняется.

## 7. Полный результат

Для каждого исходного пункта укажи: исправлено / уже исправлено / нужно решение /
явно исключено пользователем / неприменимо с доказательством / не удалось с причиной.
Перечисли файлы, результаты проверок и ограничения, модель/effort и ограничения выбора,
путь worktree и `reply_map`, ответы N из всех исправленных inline, закрытые threads и
оставшиеся ссылки с причинами. Не скрывай необязательные правки за счётчиком.

Коммит/push выполняй по отдельному основанию в запросе; повторно уже данное разрешение
не спрашивай. После разрешённого push заверши ожидающие ответы/resolve. Покажи diff:
исправления сами по себе не означают, что новый код уже прошёл независимое ревью.
