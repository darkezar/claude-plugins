# Синхронизация локалей

Работа с ключами детерминированная — поэтому её можно и проверять, и чинить автоматически.
Работа с **переводом** — нет: перевод придумывать нельзя.

## Шаг 1. Найди устройство локализации

Не предполагай — посмотри.

```bash
find . -path ./node_modules -prune -o \( -iname '*i18n*' -o -iname '*locale*' -o -iname '*lang*' \
  -o -iname '*translation*' \) -print 2>/dev/null | head -20
```

Определи:

- **какие локали поддержаны** и какая основная (фолбэк);
- **формат словаря** — плоский объект, вложенный, по файлу на неймспейс, PHP-массив, JSON, YAML;
- **как достают строку** в коде — хук, функция, хелпер, компонент;
- **типизированы ли ключи** — если да, отсутствие ключа ловится типами, и приоритет правки выше.

## Шаг 2. Сверь полноту

Собери множество ключей каждой локали и сравни с основной.

```
Локали: <список>, основная: <какая>
Ключей в основной: N
Отсутствуют в <локаль>: N — перечислить
Лишние в <локаль> (нет в основной): N — перечислить
```

Лишние ключи — тоже сигнал: чаще всего это следы удалённой функциональности либо опечатка
в имени. Удалять их **не** механическая правка, только сообщить.

## Шаг 3. Что чинится автоматически

**Недостающий ключ.** Добавляется во все локали, где его нет. Значение:

- в основную локаль — текст, который был захардкожен, либо тот, что дал автор;
- в остальные — **значение основной локали как заглушка**, и обязательно перечисли эти ключи
  в отчёте как требующие перевода. Не выдумывай перевод сам, даже если язык знаешь: неверный
  перевод хуже видимой заглушки, потому что его никто не заметит.

**Захардкоженная строка в интерфейсе.** Выносится в ключ: имя — по смыслу и по конвенции
соседних ключей, значение — исходный текст, в коде — обращение через принятый в проекте способ.

**Порядок ключей.** Если в словарях он алфавитный или сгруппированный — сохрани конвенцию,
не дописывай в конец файла вопреки ей.

## Шаг 4. Что не чинится

- **Перевод строк** — только человек или переводчик.
- **Удаление лишних ключей** — они могут использоваться динамически (`t[key]`), и поиск по коду
  этого не докажет.
- **Переименование существующих ключей** — ломает все места использования.
- **Строки вне интерфейса** — логи, технические идентификаторы, ключи API, тестовые фикстуры.
  Их выносить в локали не надо.
- **Склейка из кусков.** Если в коде строка собирается конкатенацией, это отдельная проблема
  (в разных языках порядок слов другой) — сообщи, но не переделывай на глаз: нужна
  параметризованная строка, а её формулировка — решение автора.

## Отчёт

```
## Локализация

Локали: <список> | Основная: <какая> | Формат: <какой>

### Добавлено ключей: N
- `<ключ>` → <в какие локали>, значение-заглушка из основной

### Требуют перевода: N
- `<ключ>` в <локаль> — сейчас стоит текст основной локали

### Вынесено строк из кода: N
- [file:line] "<текст>" → `<ключ>`

### Оставлено
- <что и почему: перевод / динамические ключи / конкатенация / не интерфейс>
```
