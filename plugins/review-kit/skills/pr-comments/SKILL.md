Выложи **все уникальные замечания** готового отчёта в PR. Важное — inline, остальное —
блоком `suggestion` в тексте review. Механические правки тоже публикуются обязательно.

## Условие запуска

Нужен **готовый отчёт** этой сессии: `agent-full-review`, `/review` или точечного ревьюера. Если
отчёта нет, скажи об этом и предложи сначала `/agent-full-review`. Своё ревью здесь не
проводится: выкладывается то, что уже найдено.

Чей PR — не важно. Выложить ревью в PR программиста — основной случай этой команды.

## Шаг 1. PR и проверенный коммит

Найди PR тем же порядком, что `agent-full-review` в шаге 0.5: номер или ссылка из аргументов,
PR текущей ветки, PR по коммиту. Несколько подходящих PR требуют выбора пользователя
до записи. Не нашёлся — скажи и остановись.

Номера строк в отчёте относятся к коммиту, который ревьюили, а GitHub крепит комментарий к строке
конкретного коммита PR. Поэтому проверенный коммит обязан быть головой PR:

```bash
gh pr view <номер> --json headRefOid,baseRefName --jq '.headRefOid + " " + .baseRefName'
```

Проверенный коммит — тот, что записан в журнал этим прогоном (или `HEAD` на момент ревью).

| Ситуация | Что делать |
|---|---|
| проверенный коммит = голова PR | выкладывать |
| проверенного коммита нет в PR — не запушен | остановись: сначала push, иначе строки укажут не туда |
| в PR есть коммиты новее проверенного | остановись: строки могли уехать, нужен повторный `/agent-full-review` |
| ревьюились незакоммиченные изменения | остановись: у таких строк нет коммита, к которому их прикрепить |

Правки после ревью, которые лежат в дереве незакоммиченными (например от `--fix`), выкладке не
мешают: голова PR от них не меняется.

## Шаг 2. Полный список и размещение

Возьми весь готовый отчёт, включая «Механические», «Предложения», «Упрощения», замечания
по локализации, форматированию и мёртвому коду.
Не ограничивайся блокерами, полем `open` или замечаниями с `файл:строка`.
Схлопни только смысловые дубли, сохранив самостоятельные проблемы и явные ограничения
пользователя на публикацию.

Составь локальный список для сверки: каждому уникальному замечанию назначь идентификатор
и одно место — новый inline, новый блок в body или ранее опубликованное замечание со ссылкой.
Сохрани его приоритет, категорию, файл/строку при наличии, проблему и предложенную правку.

«Важное» — «Критично»/«Важно», CRITICAL/WARNING, P0–P2; SUGGESTION, P3, предложения
и мелочи относятся к остальному. Ориентируйся на значение приоритета исходного
ревью, не переоценивай его заново. Механический характер правки не отменяет высокий приоритет.

Inline допускает только строки кусков **проверенного** diff PR (`git diff -U3 <merge-base>
<head_sha> -- <файл>`), включая три строки контекста. В `@@ -a,b +c,d @@` старая сторона —
`a..a+b-1`, новая — `c..c+d-1`; удаление привязывай к старой стороне.

| Замечание | Куда |
|---|---|
| важное, строка внутри куска | inline, `side: RIGHT` |
| важное, диапазон `файл:10-14` внутри одного куска | inline к диапазону: `start_line: 10`, `line: 14` |
| важное про удалённый код, строка в старой стороне куска | inline, `side: LEFT`, старый номер |
| важное без допустимой привязки к diff | body, раздел «Важное вне диффа», с причиной невозможности inline |
| все остальные замечания, даже с точной строкой в diff | body, блок `suggestion`: механические, мелкие, предложения, упрощения и отложенное |

Несколько важных замечаний к одной строке — один inline с отдельным описанием каждого.
Мелкие замечания к этой же строке остаются в `suggestion`. Если важное нельзя корректно
прикрепить, сохрани исходный файл/строку в «Важное вне диффа»: не придумывай номер строки
и не понижай приоритет ради размещения.

Устаревший аргумент `важные` выделяет важное inline; остальные пункты остаются в `suggestion`.

## Шаг 3. Не повторяй выложенное

Получи текущий логин через `gh api user --jq .login` и задай `VIEWER_LOGIN`.
Учитывай маркеры только комментариев/reviews этого аккаунта, общий для обоих клиентов:

```bash
gh api "repos/{owner}/{repo}/pulls/<номер>/comments" --paginate \
  --jq '.[] | select(.user.login == "<VIEWER_LOGIN>") | select(.body | contains("<!-- review-kit:inline -->")) | {path, line, original_line, body, html_url}'
gh api "repos/{owner}/{repo}/pulls/<номер>/reviews" --paginate \
  --jq '.[] | select(.user.login == "<VIEWER_LOGIN>" and .state != "PENDING") | select((.body // "") | (contains("<!-- review-kit:inline -->") or contains("<!-- review-kit:suggestions -->"))) | {body, html_url, commit_id}'
```

Подставь проверенный логин в фильтры; чужой маркер не доказывает публикацию этой команды.
Читай **оба источника полностью**, не обрезай `body`: предложения могут быть в конце
длинного review. Маркеры общие для Claude и Codex. Старые разделы «Вне диффа» тоже учитывай.
Замечание уже опубликовано, если совпадают место и суть, независимо от размещения inline/body.
Для inline сверяй `line` или `original_line`; один номер без совпадения проблемы — не дубль.
Не считай ранее опубликованным пункт, от которого в PR остался только счётчик без содержания.
Повышение приоритета, существенное уточнение проблемы или другое исправление — новые сведения,
их нельзя скрывать как дубль старого пункта. Сохрани связь с прежним обсуждением.

Дубли учитывай по [сверке полноты](#сверка-полноты). Если новых пунктов/сведений о
закрытых нет, новый review не создавай.

Замечания, которые повторный прогон признал закрытыми, перечисли в тексте ревью разделом
«Закрыто с прошлого ревью». Обсуждения не закрывай — это решает человек, который их читает.

## Шаг 4. Текст комментария

```
<!-- review-kit:inline -->
**Критично** · безопасность

<что не так и чем это стреляет — одна-две фразы>

<что сделать>
```

- Важность — как в отчёте: **Критично**, **Важно**, **Предложение**, **Упрощение**. После точки —
  зона ревьюера.
- Язык — язык отчёта.
- Блок ```` ```suggestion ```` — только когда правка механическая и заменяет ровно
  прокомментированные строки **в inline-комментарии**: тогда автор сможет применить замену.
  Если вариантов несколько или затронуты другие строки — опиши решение словами.
- Секрет, токен, пароль, персональные данные из кода в комментарий не цитируй: напиши, что они
  там есть и где. PR читают больше людей, чем код.
- Полная публикация может раскрыть детали уязвимости до исправления, в том числе в коде
  базы. Соблюдай заданный пользователем объём публикации; это не причина молча скрывать
  находку. Секретные значения по правилу выше не публикуй.
- Строку `Подтвердили: <агенты>` из отчёта не переноси: автору PR важна проблема, а не то, кто
  её нашёл.

Блок `suggestion` **в body review** — общий текстовый список остальных замечаний, не
применяемый патч. Для каждого пункта укажи категорию/приоритет, файл/строку при наличии,
суть, причину и требуемую или необязательную правку. Не вставляй произвольную замену кода
как применяемую suggestion без inline-привязки и не обещай кнопку применения такого блока.
Механические и мелкие пункты не переноси inline ради этой кнопки.

## Шаг 5. Отправка

Отправляй **одним ревью**, чтобы автор видел проверку целиком. Исключение — ограничения
GitHub, требующие нескольких частей, как описано ниже.

### Сверка полноты

Один локальный реестр связывает каждый уникальный пункт с содержанием и ровно одним местом:
новым inline (**I**), «Важное вне диффа» (**O**), `suggestion` (**S**) или прежней публикацией
текущего аккаунта со ссылкой (**D**). **T = I + O + S + D** считает находки, не комментарии.
Счётчик без содержания не покрывает пункт. Не пропускай мелкое/без строки ради краткости.
Только мелкие находки тоже требуют body review при пустом `comments`.

Сверяй реестр с окончательным payload до POST и с прочитанными фактическими body/comments
после него. При 422, таймауте или разделении на части используй тот же реестр:
принятое повторно не отправляй, непокрытое перечисли с причиной. Полная отправка возможна
только при подтверждении каждого пункта, включая body каждой части.

Если полный payload превышает ограничения GitHub, раздели его на явно пронумерованные
части с общей сверкой покрытия вместо обрезания отчёта. Один review — обычный вариант,
полнота при достижении лимитов важнее числа частей.

Сериализуй тело JSON-библиотекой в файл по [правилам артефактов](../../references/review-artifacts.md):

```json
{
  "commit_id": "<голова PR>",
  "event": "COMMENT",
  "body": "<!-- review-kit:inline -->\n🤖 **Агентное ревью** · NEEDS WORK\n\n...",
  "comments": [
    {"path": "src/a.php", "line": 42, "side": "RIGHT", "body": "..."},
    {"path": "src/b.php", "start_line": 10, "start_side": "RIGHT", "line": 14, "side": "RIGHT", "body": "..."}
  ]
}
```

```bash
gh api "repos/{owner}/{repo}/pulls/<номер>/reviews" --method POST --input <файл> --jq '.html_url'
```

`event` — всегда `COMMENT`. Ревью уходит от имени того, кто запустил команду, и `APPROVE` или
`REQUEST_CHANGES` от агента выглядели бы решением этого человека. К тому же автору PR GitHub
не даёт ни одобрить свой PR, ни вернуть его на доработку, а `COMMENT` работает везде.

Текст ревью:

````markdown
<!-- review-kit:inline -->
🤖 **Агентное ревью** · <вердикт отчёта>

<одна строка: что проверено — коммит, состав ревьюеров>
Всего уникальных: <T>. Новых inline: <I>; важных вне diff: <O>; в suggestion: <S>;
уже опубликовано: <D>. T = I + O + S + D.

**Важное вне диффа**
- [R1] <приоритет> · `файл:строка` — <проблема, последствие, решение, почему нет inline>

<!-- review-kit:suggestions -->
**suggestion — остальные замечания**
```suggestion
1. [R2] Механическое · файл:строка — <что не так, почему, что исправить>
2. [R3] Необязательное упрощение · файл:строка — <предложение и причина>
```

**Уже опубликовано**
- [R4] <краткая суть> — <ссылка на прежний комментарий или review>

**Закрыто с прошлого ревью**
- `файл` — <суть>
````

Пустые разделы не пиши.
Перед каждым POST ещё раз проверь голову PR и допустимость привязок к проверенному diff.

Если GitHub отказал:

- **422, строка не найдена в диффе** (`Line could not be resolved`, `must be part of the diff`) —
  одна плохая строка роняет всё ревью. Сверь строки с кусками ещё раз, сомнительные перенеси в
  «Важное вне диффа» с сохранением приоритета и примени [сверку полноты](#сверка-полноты).
  Всего не более двух POST-попыток; затем покажи остаток.
- **422 про незавершённое ревью** (`one pending review`) — у этого человека в PR лежит черновик
  ревью, начатый в браузере. Скажи отправить или удалить его там. Сам черновик не трогай: в нём
  чужая незаконченная работа.
- **403 или 404** — нет прав на PR. Скажи об этом и остановись: отчёт в сессии остаётся.
- **Таймаут/обрыв без определённого результата** — перечитай reviews и comments с пагинацией
  и примени [сверку полноты](#сверка-полноты) до возможного повтора.

После успешной отправки прочитай body созданного review и его комментарии:

```bash
gh api "repos/{owner}/{repo}/pulls/<номер>/reviews/<review-id>"
gh api "repos/{owner}/{repo}/pulls/<номер>/reviews/<review-id>/comments" --paginate
```

Подтверди результат по [сверке полноты](#сверка-полноты).

## Шаг 6. Итог

Две-три строки:

- ссылка на ревью (`html_url` из ответа);
- число уникальных замечаний, сколько inline, сколько важных вне diff, сколько в `suggestion`,
  сколько уже опубликовано со ссылками и сколько осталось неотправленным (при успехе — 0);
- если остановился на шаге 1 — почему и что сделать.
