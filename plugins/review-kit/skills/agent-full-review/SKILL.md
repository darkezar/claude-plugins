Запусти ревью-агенты **параллельно** по текущей ветке и собери результаты в один отчёт.
Прочитай [общую политику полного ревью](../../references/balanced-review.md): круги,
влияние изменений, экономия проверок, матрица безопасности, CI и решение о мерже.

## Шаг 0. Контекст прогона

**Если в аргументах номер или ссылка PR** — ревьюится его ветка. Сравни голову PR с `HEAD`:

```bash
gh pr view <номер> --json headRefOid,headRefName --jq '.headRefOid + " " + .headRefName'
git rev-parse HEAD
git status --short
```

Совпадают — работай как есть. Не совпадают и дерево чистое — переключись `gh pr checkout <номер>`.
Есть незакоммиченные изменения — остановись и скажи: переключение смешает их с чужой веткой.

Выполни скилл `detect-stack` и получи:

- `BASE_BRANCH` и `BASE` (хеш merge-base) — база сравнения;
- зафиксируй `HEAD_SHA` и `BASE_SHA` (вершина базовой ветки, для PR — `headRefOid` и
  `baseRefOid` из `gh pr view`). `BASE_SHA` для CI не равен merge-base;
- список активных картриджей стека (их может быть несколько: фронт + бэк в монорепо).

Затем посмотри, что реально затронул дифф:

```bash
git diff --name-only "$BASE"...HEAD
git diff "$BASE"...HEAD
```

Если дифф пустой — проверь незакоммиченное (`git diff`, `git diff --cached`) и ревьюй его.
Такой прогон проверяет не коммит, а рабочее дерево: в шаге 4 он пишется только локально,
с `"dirty":true`.

## Шаг 0.5. Первый это прогон или повторный

Команда одна на все случаи: какой это прогон и сколько он должен стоить, она решает сама по
журналу. Пользователь аргументов не передаёт и не обязан — режим определяется здесь.

Журнал ведётся в двух местах, оба читай молча.

**PR ветки** определи сразу — он нужен и здесь, и при записи в шаге 4. По порядку, до первого
найденного:

1. номер или ссылка из аргументов;
2. PR текущей ветки: `gh pr view --json number,url,author`;
3. PR по коммиту — так он находится, когда ветка взята под другим именем, лежит в worktree или
   `HEAD` отсоединён. Это обычный случай, когда смотришь чужую ветку:
   ```bash
   SHA=$(git rev-parse HEAD)
   gh api "repos/{owner}/{repo}/commits/$SHA/pulls" \
     --jq ".[] | select(.state == \"open\" and .head.sha == \"$SHA\") | \"\(.number) \(.user.login)\""
   ```

Не нашёлся ни одним способом — PR нет.

**Ключ ветки** в журнале — `git branch --show-current`. При отсоединённом `HEAD` имени нет, тогда
ключ — `pr-<номер>`.

**Локальный журнал** — строка JSON на прогон:

```bash
LOG="$(git rev-parse --git-common-dir)/review-log.jsonl"
[ -f "$LOG" ] && grep -F "\"branch\":\"<ключ ветки>\"" "$LOG" | tail -5
```

Он лежит в служебном каталоге git: не попадает в дифф, не требует `.gitignore` и общий для всех
worktree одного репозитория.

**Журнал в PR** — если PR есть. Он переживает смену машины и общий для всех, кто ревьюит ветку:

```bash
gh api "repos/{owner}/{repo}/issues/<номер>/comments" --paginate \
  --jq '.[] | select(.body | contains("<!-- review-kit:log -->")) | {id, body}'
```

`--paginate` обязателен: без него приходят только первые 30 комментариев, и в обсуждаемом PR
журнал теряется. Если комментариев-журналов несколько, действует последний.

Возьми последний записанный коммит `LAST` и открытые замечания прошлого прогона. Строки с
`"dirty":true` пропускай: проверенного коммита у них нет. Открытые замечания — поле `open`
локальной строки, а если её нет — текст вердикта в строке журнала PR. После rebase/переписывания
базы или смены правил — первый прогон; сообщения коммитов не доказывают прежнее покрытие.
При отсутствии полных оснований старого анализа не считай его кэшем всех зон.

| Что в журнале | Режим |
|---|---|
| записей по ветке нет | **первый** |
| `LAST` совпадает с `HEAD` | **без изменений** |
| сверху есть коммиты | **повторный** |

Явная просьба заново проверить с другой моделью/effort или перепроверить результат отменяет
использование прежнего вердикта: выполни новый анализ запрошенной области с выбранными
настройками. Для такого анализа переопредели режим на **первый** (`mode: first`), даже
если `LAST` равен `HEAD` или прирост пустой. Правила пропуска «без изменений» и пустого
прироста к нему не применяются; завершённый новый прогон записывается по шагу 4.

**Без изменений** — сравни также базу, дерево, правила и область запроса. Продвижение базы
сначала требует оценки влияния по правилам повторного прогона, даже при том же `HEAD`.
При достоверном прежнем покрытии не запускай агентов, переиспользуй анализ и открытые замечания, но обнови
CI и решение о мерже. Смена CI не добавляет круг анализа (`analysis_reused: true`).
Изменившийся статус обнови в журнале с временем; одинаковые записи не дублируй.

**Повторный** — посчитай прирост: собственные коммиты ветки после `LAST`, без слияний с базовой
веткой и без того, что из неё пришло.

```bash
git log --no-merges --format='%h %s' "$LAST"..HEAD --not "origin/$BASE_BRANCH"
INC_FILES=$(git log --no-merges --name-only --format= "$LAST"..HEAD --not "origin/$BASE_BRANCH" | sort -u)
git diff --stat "$LAST" HEAD -- $INC_FILES     # строки прироста
git diff --shortstat "$BASE"...HEAD            # строки всего диффа ветки — для сравнения
```

Дополни `INC_FILES` файлами разрешённых конфликтов в merge-коммитах: `--no-merges` их
пропускает. Отдельно сравни прошлый `base_sha` с `BASE_SHA`, оцени влияние новых изменений
базы на PR. При отсутствии прежней базы нельзя объявить пустой прирост безопасным.

## Шаг 1. Реши, кто нужен

Фиксированного набора нет, ни один агент не запускается по привычке. Каждый прогон стоит денег,
а лишний ревьюер ещё и разбавляет отчёт пустыми секциями.

### 1.1. Первый прогон

Классифицируй весь дифф ветки (1.3) и выбери агентов (1.4–1.6).

### 1.2. Повторный прогон

Проверь закрытие замечаний и последствия правок через `impact` по общей политике.
Номер круга — последний `analysis_round` + 1 при новом анализе; при одном обновлении CI
не увеличивается. Старые записи без номера допускают приблизительный счёт с явной пометкой.

| Прирост | Кого запускать |
|---|---|
| пустой — только слияния/продвижение базы | сначала влияние базы; без него переиспользуй анализ и обнови CI, иначе проверь затронутые связи |
| только тесты, комментарии, документация, форматирование | сам проверь смысл и влияние; запускай нужные проверки, не весь набор по привычке |
| обычный | `branch` — прирост и затронутые старые файлы целиком |
| задевает триггеры `security`/`auth` из картриджа | плюс `security`/`auth`, по приросту (асимметрия 1.5 в силе) |
| задевает явные триггеры `performance`/`design` | плюс он, по приросту |
| большой прирост или новые модули | оцени границу влияния; полный прогон только при потере достоверности прежнего покрытия |

`simplify` повторно нужен лишь для нового существенного дублирования/сложности или явного
запроса; косметические предложения не блокируют мерж и не запускают новый круг сами по себе.

Ревьюеру повторного прогона передай список коммитов прироста, `INC_FILES`, открытые замечания
прошлого прогона и задачу: «по каждому замечанию — закрыто или нет и почему; проверь прирост
и затронутых вызывающих/потребителей, включая неизменённые уже проверенные файлы;
расширяй область до подтверждённой границы влияния». Не перечитывай прочее без причины.

### 1.3. Классифицируй дифф


Перед выбором агентов ответь себе на четыре вопроса — коротко, по существу:

1. **Что за изменение?** Новая функциональность, исправление бага, рефакторинг, правка
   конфигурации, обновление зависимостей, документация, тесты.
2. **Какие слои затронуты?** Интерфейс и стили · бизнес-логика · данные и схема · транспорт,
   роуты и обработчики · конфигурация и сборка · тесты · документация.
3. **Пересекается ли граница доверия?** Приходят ли в изменённый код данные извне; решается ли
   в нём, кому что можно; участвуют ли деньги, персональные данные, секреты, права.
4. **Каков масштаб?** Сколько файлов и строк, сосредоточено это в одном месте или размазано.

### 1.4. Выбери агентов


По каждому прими решение **осознанно** и обоснуй одной строкой.

| Агент | Запускать, когда | Не запускать, когда |
|---|---|---|
| `agent-branch-reviewer` | изменена логика на любом языке | правка только документации, локалей, ассетов или версий зависимостей |
| `agent-security-reviewer` | код принимает внешний ввод, ходит в БД или сеть, работает с секретами, файлами, платежами, персональными данными | изолированная логика без внешнего ввода: чистые функции, форматирование, верстка, тесты |
| `agent-auth-reviewer` | затронуты вход, сессии, токены, права, роли, защищённые эндпоинты, деньги, чувствительные действия | ничего из перечисленного дифф не касается |
| `agent-performance-reviewer` | новые или изменённые запросы к БД, миграции, циклы по данным, списки, анимации, изображения, тяжёлые зависимости | логика без данных и без рендера, конфигурация, тексты |
| `agent-design-reviewer` | затронуты вёрстка, стили, токены темы, UI-примитивы, строки локализации | в диффе нет интерфейса, либо в проекте нет дизайн-системы |
| `agent-simplify` | содержательный объём кода — примерно от сотни строк либо от трёх файлов | косметическая правка, единичный фикс в пару строк, авто-форматирование |

Конкретные пути и ключевые слова для двух средних строк бери из раздела «Триггеры условных
ревьюеров» каждого активного картриджа стека — они проверяются и по путям, и по содержимому диффа.

### 1.5. Асимметрия ошибки


Цена промаха разная, поэтому и запас разный:

- **`security` и `auth` — сомневаешься, включай.** Пропущенная дыра дороже лишнего прогона.
  Достаточно слабого признака: дифф трогает роут, запрос к БД, обработку ввода, что-то денежное.
- **`design` и `performance` — включай только по явному признаку.** Здесь лишний прогон не
  страхует ни от чего, а только добавляет шум и стоимость.
- **`branch`** — практически всегда при изменении кода; исключение только для неисполняемых файлов.
- **`simplify`** — по объёму, а не по теме.

### 1.6. Крайние случаи


- **Дифф тривиален** (несколько строк, одно место, нет границы доверия) — не разворачивай
  фан-аут. Запусти одного `agent-branch-reviewer` либо предложи пользователю команду `/review`,
  которая сделает всё одним проходом дешевле.
- **Дифф не содержит кода вообще** (документация, тексты, картинки) — не запускай никого,
  скажи об этом прямо и коротко опиши изменение.
- **Не выбралось ни одного агента, но код в диффе есть** — это подозрительно. Перепроверь
  классификацию, и если сомнения остались, запусти `agent-branch-reviewer`.

### 1.7. Модель и effort

Выбери настройки отдельно для каждой выбранной зоны по
[общей политике](../../references/execution-routing.md), разделы «Решение по задаче»,
«Claude Code» и «Отчёт». Передавай `model` и `effort` параметрами Agent tool, если они
поддерживаются. Одних слов в промпте недостаточно. Повторная проверка прав или денег
не становится простой из-за режима прогона; выбор состава и выбор глубины независимы.

### 1.8. Аргументы — необязательны

Обычный запуск — без аргументов. Аргументы оставлены для редких случаев и отменяют выбор режима
и состава; состав всё равно покажи в отчёте.

- `all` / `full` — все шестеро по всему диффу; модель и effort каждому по задаче;
- `min` / `core` — только `branch`;
- имена агентов через запятую (`security,auth`) — ровно они;
- номер или ссылка PR — ревьюить ветку этого PR (Шаг 0), журнал писать в него; режим и состав
  при этом выбираются как обычно;
- `--comment` — после отчёта и записи журнала запустить скилл `pr-comments`: все замечания
  уйдут в PR, важное inline, остальное блоком `suggestion` в body review;
- `--fix` — после отчёта исправить все готовые замечания через `apply-fixes`, включая
  необязательные предложения; спрашивать только при существенной неоднозначности. Вместе с
  `--comment` — сначала комментарии, потом правки. Включает ответы на исправленные inline
  и resolve полностью решённых в PR обсуждений по правилам `apply-fixes`;
- `--no-pr-log` — не писать журнал в PR (см. Шаг 4), локальная запись остаётся.

## Шаг 2. Запуск

Запусти всех выбранных агентов через Agent tool **в одном сообщении**, чтобы они шли параллельно.

Каждому передай в промпте:

1. `BASE_BRANCH` и `BASE` — чтобы агент не пересчитывал базу и не промахнулся;
2. имена активных картриджей: «прочитай скиллы `stack-…` перед ревью»;
3. **состав прогона** — кто ещё запущен и кто пропущен, с назначением добора;
4. **что нельзя запустить в этом окружении** — если ты уже знаешь, что тестов, линтера или
   статанализатора здесь не прогнать (нет рантайма, нет доступа к контейнерам, нет сети), скажи
   это прямо и потребуй писать «не прогонялось» вместо «passed». Иначе каждый агент потратит
   несколько ходов, чтобы выяснить это самостоятельно, — и так по разу на каждого.
5. **модель и effort** — по разделу 1.7, также реальными параметрами запуска;
6. в повторном прогоне — коммиты прироста, `INC_FILES`, влияние базы, затронутые старые
   файлы, номер круга и открытые замечания (1.2).

Составь `check_plan` по общей политике. Назначь одного ответственного за запуск проверок,
передай остальным результаты/ограничения, чтобы тесты не дублировались. Тяжёлые проверки
передавай только при конкретном риске; недоступность необходимой проверки отрази в решении.

Дополнительно напомни строкой: **находки в чужой зоне — одной строкой в «Замечено попутно»,
без разворачивания**. У агентов это правило записано, но именно оно первым едет, когда находка
кажется важной. Стоимость промаха видна сразу: агенты не видят друг друга, поэтому одна заметная
проблема легко приезжает в отчёт четырьмя развёрнутыми пересказами, за каждый из которых
пользователь заплатил.

Зоны у агентов разведены, чтобы одна и та же проблема не приезжала в отчёт по четыре раза.
Обратная сторона: если ревьюер не запущен, его зона остаётся вообще никем не покрытой. Поэтому
состав прогона обязателен, и вместе с ним ты **явно назначаешь добор**.

Правило назначения: зону пропущенного агента добирает тот из **запущенных**, чья зона ближе.

| Пропущен | Добирает | Если и он не запущен |
|---|---|---|
| `auth` | `security` | `branch` |
| `performance` | `branch` | не добирается |
| `design` | `branch` | не добирается |
| `simplify` | никто — качество не критично для мержа | — |

Добор означает: только явные и грубые проблемы, с пометкой `(добор за <агент>)`. Это не
полноценное ревью чужой зоны.

**Важное исключение.** Если ты пропустил агента осознанно — потому что его тема в диффе
отсутствует, — добор за него назначать не надо: покрывать нечего. Назначай добор только когда
пропуск продиктован экономией, а не отсутствием предмета. Так и напиши в промпте, чтобы агент
не тратил ходы на поиск того, чего нет.

Пример строки для промпта: «Запущены: branch, security. Пропущены: auth (нет изменений в
авторизации — добор не нужен), design (в проекте нет UI — добор не нужен), performance
(изменения не затрагивают данные и рендер — добор не нужен), simplify (дифф 40 строк)».

## Шаг 3. Сводный отчёт

Включай только секции тех агентов, которых запускал. Пропуск отмечай одной строкой с причиной —
внятной, а не «триггер не сработал»: пользователь должен видеть, что состав выбран осмысленно,
и суметь возразить.
Укажи выбранные модель и effort по ролям, причину повышения и ограничения их применения.
Сохрани все уникальные замечания, включая механические, мелкие, предложения и упрощения.
Итоговая статистика не заменяет их описание: `pr-comments` должен получить полный список,
даже если предложения не влияют на вердикт или явно отложены пользователем.
Перед итогом обнови CI для зафиксированной пары SHA, заполни общую таблицу безопасности
из доказательств и выведи `impact`/фактические проверки по общей политике. Они обязательны
и без отдельных security/auth агентов; пропущенное не становится «проверено».

### Сведение дублей

Одна проблема — одна запись. Дубли неизбежны: агенты идут параллельно и не видят друг друга,
поэтому заметное место в диффе притягивает сразу нескольких.

Сводя, держись двух правил:

- **Запись живёт в секции того, чья это зона** — не того, кто написал первым или подробнее.
  Если владелец зоны описал проблему беднее коллеги, возьми лучшую формулировку, но оставь
  её в его секции.
- **Строка из «Замечено попутно» — тот же дубль.** Схлопывай её в полноценный пункт владельца
  зоны и не тащи раздел «Замечено попутно» в сводный отчёт отдельной секцией.

Под каждой сведённой записью добавь `Подтвердили: <агенты>` — совпадение независимых ревьюеров
это сигнал, а не шум, и пользователю он полезен.

Если одну и ту же строку кода отметили **четверо и больше**, скажи об этом отдельной строкой в
«Итоге». Либо место действительно узловое, либо границы зон в этом прогоне не сработали — и то
и другое стоит знать.

```
# Полный ревью ветки

База: <BASE_BRANCH> (merge-base <короткий хеш>)
Стек: <активные картриджи>
Характер изменений: <одна строка: что это за правка и какие слои затронуты>
Прогон: #<N>, первый | повторный — прирост <K> коммитов, <M> файлов поверх <хеш>
(#<N-1>, <когда>, вердикт <вердикт>; открытых замечаний было <O>)

Запущены: <агенты> — <по одной короткой причине на каждого>
Пропущены: <агенты> — <по одной короткой причине на каждого>

<Находки по фактически проверенным зонам, без пустых секций>
<Покрытие безопасности — общая таблица с основаниями>
<Impact: перечитанные старые файлы, переиспользованное покрытие>
<Выполненные проверки и ограничения>

### Вердикт: READY TO PR / READY AFTER FIXES / NEEDS WORK
Решение: МЕРЖИТЬ / МЕРЖИТЬ ПОСЛЕ <условие> / НЕ МЕРЖИТЬ
CI: <статус, head/base SHA, время, ссылка/ограничение>
Исправлено: <подтверждённые исправления, известные коммиты>
Условия / порядок деплоя: <если применимо>
Следующий шаг: <одна строка>
```

В повторном прогоне добавь перед «Итогом» раздел «Замечания прошлого прогона»: по каждому —
закрыто или нет, одной строкой.

Вердикт:

- `NEEDS WORK` — есть хоть одно замечание «критично» или `FAIL` у безопасности либо авторизации.
- `READY AFTER FIXES` — критичного нет, но есть «важно» по корректности, данным, деньгам или
  тестам. Правки внести; полного повторного ревью они не требуют.
- `READY TO PR` — ни критичного, ни важного. Предложения и упрощения мержу не мешают.

`REQUEST CHANGES` ревьюера кода без единого «критично» — это `READY AFTER FIXES`, а не
`NEEDS WORK`. Иначе вердикт не отличает блокер от мелочи, и ветку гоняют по кругу полных ревью.

Следующий шаг по вердикту:

- `NEEDS WORK` — исправить критичное и снова запустить эту же команду: она сама поймёт, что
  прогон повторный, и проверит правки с их последствиями;
- `READY AFTER FIXES` — внести правки (`/apply-fixes`); следующая проверка выбирается по
  влиянию изменений, без гарантии одного агента;
- `READY TO PR` — анализ кода завершён; допуск к мерджу определяется отдельно по CI,
  полноте необходимого покрытия и конкретным зависимостям из общей политики.

Если обнаружен новый существенный риск, расширь нужную проверку в текущем запросе.
Недоступную необходимую проверку укажи ограничением и условием решения, не выдавай допуск.

Если PR чужой — его автор не тот, кто запускает ревью (`gh api user --jq .login`), — и замечания
есть, а `--comment` не передан, добавь строку: выложить их программисту у строк можно командой
`/pr-comments`. Сам не выкладывай.

Если замечания есть — укажи, что `--fix`/`apply-fixes` применяет весь готовый список,
включая предложения, с вопросами только при неоднозначном решении. Без запроса исправлений
само применение не запускай.

Если кто-то из агентов заметил, что `CLAUDE.md` противоречит коду, вынеси это отдельной строкой
в «Итог». Агенты читают этот файл и доверяют ему, поэтому устаревшее правило в нём отравляет
все последующие ревью. Чинится командой `/context-refresh`.

## Шаг 4. Запиши прогон

Отчёт живёт в одной сессии и исчезает вместе с ней. Запись — то, что от прогона останется.

**Локально — после завершённого анализа или изменившегося внешнего статуса**, одной строкой.
Сериализуй полный JSON-отчёт в `REPORT_FILE` вне проверяемого дерева: время `ts`, ключ `branch`,
полные `sha`/`base_sha`, `base` (имя ветки), `mode`, `dirty`, `agents`, кодовый `verdict`,
массивы `findings` (все находки) и `open` (только важное/критичное), выполненные `checks`.
Добавь `execution`, `impact`, `check_plan`, `security_coverage`, `ci`, `merge_decision`,
`conditions`, `review_round` и `analysis_round` по общей политике. `analysis_reused: true`
допустимо только для прежнего анализа без нового кода/влияния базы; номер не увеличивается.
Для нового анализа сохрани также основания повторного использования: правила, область,
стек и проверенные зависимости. Перед записью сверь предмет с зафиксированным в начале;
при изменении SHA/дерева/правил обозначь устаревание, не записывай новый допуск.

```bash
LOG="$(git rev-parse --git-common-dir)/review-log.jsonl"
python3 - "$REPORT_FILE" "$LOG" <<'PY'
import json, sys
from pathlib import Path
report = json.loads(Path(sys.argv[1]).read_text())
with Path(sys.argv[2]).open("a") as stream:
    stream.write(json.dumps(report, ensure_ascii=False, separators=(",", ":")) + "\n")
PY
```

Не собирай JSON shell-интерполяцией и не удаляй кавычки из находок ради формата.

- `mode` — `first` или `followup`.
- `dirty` — `true`, если ревьюилось незакоммиченное, иначе `false`.
- `open` — незакрытые «критично» и «важно», коротко, «файл: суть». По ним следующий повторный
  прогон проверяет, что закрыто. Предложения и упрощения туда не пиши.
- `execution` — выбранные модель и effort по ролям, подтверждённые клиентом настройки
  и ограничения. Запиши их вместе с результатом нового анализа.
- Новый анализ без агентов тоже записывай с `"agents":[]`. При пустом приросте или режиме
  «без изменений» **без влияния базы и без нового анализа** сохраняй лишь изменившийся
  внешний статус; это не новый круг. Анализ влияющей базы записывай как новый круг.

**В PR — если он есть** — выполни [общую процедуру журнала](../../references/pr-review-journal.md).
`--comment` не нужен, `--no-pr-log`/запрет пользователя отключает публикацию журнала.
Локальный результат сохраняется. Не пиши незакоммиченное в PR и не добавляй дубликаты.
