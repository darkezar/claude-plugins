# Детект базовой ветки и стека

Два коротких шага, которые выполняет любая ревью-команда перед запуском агентов.

## Шаг 1. Базовая ветка

Не хардкодь `main` — в проектах встречаются `master`, `develop`, `trunk`.

```bash
# 1. Спросить у remote, что он считает главной веткой
BASE_BRANCH=$(git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null | sed 's|^origin/||')

# 2. Фолбэк: первая существующая из общепринятых
if [ -z "$BASE_BRANCH" ]; then
  for b in main master develop trunk; do
    git show-ref --verify --quiet "refs/heads/$b" && BASE_BRANCH=$b && break
  done
fi

# 3. Точка расхождения ветки с базой
BASE=$(git merge-base HEAD "$BASE_BRANCH")
echo "base branch: $BASE_BRANCH  merge-base: $BASE"
```

Дальше везде используется `"$BASE"...HEAD`, а не `main...HEAD`. Форма с тремя точками от
merge-base показывает **только изменения ветки**, без того, что уехало в базу параллельно.

Если базовая ветка не нашлась вообще (свежий репозиторий без коммитов в базе) — ревьюй
незакоммиченное: `git diff --name-only` и `git diff --cached --name-only`.

## Шаг 2. Активные стеки

Стеков может быть **несколько одновременно** — в монорепо обычно фронт + бэк. Возвращай список,
а не одно значение. Ищи маркеры до 3 уровней вложенности (корень, `apps/*`, `packages/*`,
`frontend*/`, `backend*/`, `api/`, `web/`).

```bash
# Маркеры PHP
find . -maxdepth 3 -name composer.json -not -path '*/vendor/*'
find . -maxdepth 3 \( -name artisan -o -name yii \) -not -path '*/vendor/*'

# Маркеры JS
find . -maxdepth 3 -name package.json -not -path '*/node_modules/*'
```

| Признак | Стек | Картридж |
|---|---|---|
| `artisan` рядом с `composer.json`, либо `laravel/framework` в `require` | Laravel | `stack-laravel` |
| файл `yii` / `yii.bat`, либо `yiisoft/yii2` в `require` | Yii2 | `stack-yii2` |
| `next` в `dependencies` package.json | Next.js | `stack-nextjs` |
| `expo` или `react-native` в `dependencies` | Expo / React Native | `stack-expo-rn` |
| `react` в `dependencies` **без** `next` и `react-native` | React SPA | `stack-react-spa` |

Уточнения:

- **Манифест ≠ стек.** `composer.json` или `package.json` может не содержать ни одного фреймворка
  из таблицы — например это legacy-приложение на голом PHP или набор сборочных зависимостей.
  Тогда картридж для него не подключается, и эта часть проекта ревьюится по универсальному
  чек-листу. Так и напиши в отчёте, а не подгоняй под ближайший знакомый стек.
- **Игнорируй служебные манифесты** — под `tools/`, `build/`, `scripts/`, `.github/`, `docs/`
  и в каталогах статических анализаторов. Это зависимости инструментов, а не приложение.
  Именно поэтому глубина поиска ограничена тремя уровнями: глубже начинается тулинг.
- **Next.js и React SPA взаимоисключающи** — если есть `next`, картридж React SPA не подключается.
- **Expo и React Native — один картридж.** Голый RN без Expo им же и покрывается; пункты про
  Expo-специфику (`expo-image`, SecureStore, expo-router) в таком случае применяй по факту
  наличия пакета, а не автоматически.
- Если ни один маркер не сработал — работай **только по универсальному чек-листу** агента и скажи
  об этом в отчёте одной строкой. Не выдумывай стек и не тащи чужие правила.
- Версии фреймворка бери из `composer.json` / `package.json`, а не из памяти: чек-лист может
  ссылаться на API, которого в этой версии ещё (или уже) нет.

## Шаг 3. Что передать агенту

Запуская ревью-агента, передай в промпте три вещи:

1. `BASE_BRANCH` и `BASE` (хеш merge-base) — чтобы агент не пересчитывал и не промахнулся;
2. список картриджей: «прочитай скиллы `stack-laravel` и `stack-expo-rn` перед ревью»;
3. состав прогона: кто ещё из ревьюеров запущен в этот раз — от этого зависит, какие зоны
   агент покрывает сам, а какие оставляет коллеге (см. «Границы зон» в описании агента).

## Правила проекта

Доменные правила конкретного проекта (продуктовые инварианты, запретные практики, локальные
конвенции) живут в его `CLAUDE.md` / `AGENTS.md` и попадают в контекст автоматически. Не дублируй
их в картриджах: картридж описывает **стек**, а не проект.
