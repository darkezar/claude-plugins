# Review Kit для Codex

Проведи ревью и верни подтверждённые находки. Язык — язык запроса. Явные указания пользователя
и инструкции окружения приоритетнее этого навыка. Завершённый прогон записывается локально и
в журнал PR по правилам ниже. Ревью само по себе не разрешает менять код, публиковать подробные
замечания у строк, коммитить, пушить или одобрять PR.

Пути ниже относительны к каталогу этого `SKILL.md`, не к проверяемому проекту. Определи
абсолютный путь установленного пакета по пути навыка. `PLUGIN_ROOT` в примерах — корень
`review-kit`, на два уровня выше этого файла; это локальная переменная, а не обязательная
переменная окружения. Не ищи пакет в `.claude/` или в исходном репозитории автора.

## 1. Зафиксируй предмет проверки

Прочитай применимые `AGENTS.md`, проектный `CLAUDE.md` и ссылки на документацию по затронутым
темам. При конфликте следуй инструкциям окружения и каноническим правилам проекта.

**Если передан PR:**

1. Проверь `gh auth status`. Получи каноническое имя текущего репозитория через
   `gh repo view --json nameWithOwner` и данные PR:
   `gh pr view <PR> --json number,url,baseRefName,baseRefOid,headRefName,headRefOid`.
   Убедись, что ссылка PR относится к этому репозиторию. Для другого репозитория используй
   отдельный checkout, не применяй его номера и SHA к текущему проекту.
2. База — **`baseRefOid` этого PR**, голова — **`headRefOid`**. Главная ветка репозитория
   может не быть базой PR. По URL в `git remote -v` найди remote именно базового репозитория;
   в checkout форка это может быть `upstream`, а не `origin`. Обозначь его `BASE_REMOTE`.
   Подтяни объекты через `git fetch --no-tags "$BASE_REMOTE"
   "refs/heads/<baseRefName>" "refs/pull/<number>/head"`; убедись, что оба SHA доступны.
   Если PR успел измениться, заново получи его данные и зафиксируй новую пару SHA.
3. Проверь состояние текущего дерева. Если `HEAD` равен голове PR и дерево чистое, работай в
   нём. Иначе создай временный **detached worktree** на зафиксированном SHA и читай код там.
   Текущую ветку, индекс и незакоммиченные изменения пользователя не переключай и не прячь.
   Запомни созданный путь. Отдельный worktree может не иметь зависимостей — это ограничение
   проверок, а не повод запускать установку зависимостей автоматически.
4. Пустой diff PR означает пустой diff: не подменяй его незакоммиченными изменениями.

**Если проверяется текущая ветка:** используй указанную пользователем базу. Иначе найди PR
ветки и возьми его базу; если PR нет — используй доступный `origin/HEAD`. Обнови remote refs,
когда есть доступ к сети. Если база неоднозначна, уточни её, не угадывай между `main` и
`develop`. Укажи, если проверяется только локальная, возможно устаревшая база.
Включи staged, unstaged и релевантные untracked-файлы; список последних получи через
`git ls-files --others --exclude-standard`. Не ограничивайся `git diff`, который их не показывает.

Создай снимок **до** анализа и сохрани JSON во временный файл:

```bash
python3 "$PLUGIN_ROOT/scripts/review_snapshot.py" capture --repo "$REVIEW_ROOT" \
  --base "$BASE_SHA" --head "$HEAD_SHA" --target "$TARGET" --scope "$SCOPE"
```

`TARGET` — канонический URL PR или имя текущей ветки; `SCOPE` — `auto`, `all`, `min` либо
выбранные зоны через запятую. По умолчанию `auto`. `merge_base` в ответе — точка расхождения.
Для PR читай `git diff <merge_base> <head_sha>`; для текущего дерева —
`git diff <merge_base>` плюс untracked. Параметр `--rules <путь>` можно повторять для прочитанных
проектных руководств; относительные пути разрешаются от корня проверяемого проекта.

## 2. Первый или повторный прогон

Помощник читает только локальный журнал `review-kit-codex.jsonl` в общем git-каталоге.
Комментарии PR и старый журнал Claude не являются доказательством завершённого Codex-ревью.

- `unchanged`: совпали база, голова, содержимое дерева, правила, пакет и состав запроса.
  Повтори сохранённый результат и укажи проверенные SHA. Не выдавай старые проверки за новые.
  Явная просьба перепроверить или перезапустить тесты отменяет повторное использование.
- `followup`: прежняя голова — предок текущей, база, правила, пакет и состав запроса прежние,
  оба дерева чистые. Проверь старые открытые замечания и изменения между головами, читая
  затронутые файлы и прямых потребителей. Новые границы доверия требуют security/auth заново.
  Большое изменение или новый модуль — полный прогон.
- `first`: полный diff. После rebase не сопоставляй коммиты по сообщениям. Изменение базы,
  правил, пакета или незакоммиченного содержимого требует полного прогона.

## 3. Выбери зоны и прочитай общие чек-листы

Чек-листы общие с Claude Code. Загружай только выбранные документы и их предметные разделы:
границы зоны, ключевые принципы, чек-листы. Их YAML (`model`, `tools`, `effort`, `context`),
Claude Agent/Skill tool, подготовка, журнал и шаблоны вывода **не настраивают Codex**.
Запуск, инструменты, сравнение и отчёт определяет этот навык.

| Зона | Когда нужна | Общий документ |
|---|---|---|
| branch | изменена исполняемая логика | [Корректность](../../agents/agent-branch-reviewer.md) |
| security | внешний ввод, БД, сеть, файлы, секреты или персональные данные | [Безопасность](../../agents/agent-security-reviewer.md) |
| auth | вход, сессии, права, токены, деньги или чувствительные действия | [Доступ](../../agents/agent-auth-reviewer.md) |
| performance | изменены запросы, циклы по данным, списки или тяжёлый рендер | [Производительность](../../agents/agent-performance-reviewer.md) |
| design | затронут UI и есть применимые правила дизайна | [Дизайн](../../agents/agent-design-reviewer.md) |
| simplify | существенный объём или явное дублирование | [Упрощение](../../agents/agent-simplify.md) |

Security/auth выбирай при слабом признаке; performance/design — при явном. Маленькой правке
достаточно одного прохода. `all` включает все зоны, `min` — branch с явными рисками остальных,
`security,auth` — только перечисленные зоны. Неприменимые пункты не превращай в замечания.

Стек определяй по манифестам затронутых приложений, а не всему монорепозиторию сразу.
Прочитай предметные разделы подходящих картриджей:
[Yii2](../../skills/stack-yii2/SKILL.md), [Laravel](../../skills/stack-laravel/SKILL.md),
[Next.js](../../skills/stack-nextjs/SKILL.md), [React SPA](../../skills/stack-react-spa/SKILL.md),
[Expo/React Native](../../skills/stack-expo-rn/SKILL.md).
Legacy-код не наследует правила соседнего Yii2-приложения. Команды картриджа — подсказки:
применяй реальные настройки проекта. Проектные Resource-классы, model behaviors и прочие
явные контракты приоритетнее общих советов об API и массовых обновлениях.

Если инструменты подагентов доступны и их применение разрешено текущим запросом и окружением,
делегируй независимые выбранные зоны read-only ревьюерам. Этот навык предусматривает такую
делегацию для содержательного ревью. Не используй имена Claude-агентов как типы Codex-агентов,
не переноси `opus` и его effort. При отсутствии делегации проверь зоны сам последовательно.
В отчёте честно укажи способ проверки; не имитируй независимое подтверждение.
Каждому ревьюеру передай рабочий каталог, фиксированные SHA, diff, правила, состав зон и
ограничения проверок. Проверки запускает один ответственный, чтобы не дублировать их.

## 4. Проверь и сведи результат

Прочитай изменённые файлы и прямых вызывающих/потребителей. Замечание требует конкретного
сценария, последствия и подтверждения кодом. Отделяй дефекты этого изменения от прежних проблем
и необязательных предложений. Совпадение мнений само по себе не доказывает дефект.

Найди команды проверок в применимых инструкциях, `Makefile`/`justfile`, затем
`composer.json`/`package.json` и настройках тестов. Читай тело команды: форматирование,
миграции и автофиксы меняют дерево. Используй проверяющие формы и небольшие релевантные тесты.
Учитывай контейнеры и рабочие каталоги. Недоступная зависимость или среда — «не запускалось»
с причиной. Не обещай изоляцию, которую не обеспечивает доступный инструмент или команда.

Одна проблема — одна находка. Отчёт содержит:

- предмет проверки, base/head SHA, стек, режим и выбранные зоны;
- находки с приоритетом, файлом и точной строкой, сценарием и рекомендацией;
- отдельно необязательные предложения, если они полезны;
- старые замечания: подтверждено исправление / осталось / невозможно проверить;
- фактически выполненные проверки с результатами и ограничения;
- `NEEDS WORK` для критичного, `READY AFTER FIXES` для важных исправлений,
  `READY TO PR` при отсутствии обоих. Недостаток данных отрази явно, не выдавай уверенный допуск.

Сохрани итог во временный JSON: `verdict` (один из трёх выше), `findings` (массив находок),
`open` (массив незакрытых важных/критичных замечаний), `checks` (массив команд и результатов).
Добавь `zones`, `stack`, `summary` и `limitations`, чтобы повторить контекст и ограничения
сохранённого результата без выдуманных деталей.
Строки и переводы строк сериализуй JSON-библиотекой, не shell-интерполяцией.

```bash
python3 "$PLUGIN_ROOT/scripts/review_snapshot.py" record --repo "$REVIEW_ROOT" \
  --snapshot "$SNAPSHOT_FILE" --report "$REPORT_FILE"
```

Помощник откажется записывать результат, если код или правила изменились во время ревью.
Тогда обозначь границу проверенного, а не сохраняй устаревший вердикт. Журнал локальный;
его отсутствие на другой машине означает первый прогон. История в PR дополняет этот журнал,
но не заменяет снимок для автоматического повторного использования результата.

## 5. Запиши прогон в PR

После завершённого ревью **запиши прогон в PR, если он есть**. Это часть обычного запуска,
отдельный `--comment` для журнала не нужен. Отказаться от этой записи можно явным указанием
пользователя или аргументом `--no-pr-log`; локальный журнал остаётся.

Найди PR по переданному номеру/URL, затем по текущей ветке, затем по проверенному коммиту
через `gh api repos/{owner}/{repo}/commits/<head_sha>/pulls`. Авторство PR не меняет правило:
ревью PR коллеги тоже должно оставлять запись.

Используй общий с Claude маркер `<!-- review-kit:log -->` и один комментарий-журнал.
Прочитай комментарии через `gh api repos/{owner}/{repo}/issues/<number>/comments --paginate`.
Если журнал существует — сохрани прежние строки и добавь новый прогон сверху; если нет —
создай его. Общий формат таблицы приведён в разделе «Шаг 4. Запиши прогон»
[исходного навыка](../../skills/agent-full-review/SKILL.md); остальную Claude-оркестрацию
из этого справочника не выполняй.

Запись содержит время с часовым поясом, **проверенный head SHA**, base SHA, первый/повторный
режим, фактический состав проверки, вердикт и число открытых важных/критичных замечаний.
Полные SHA возьми из снимка этого прогона, а не из текущего `HEAD`. Если голова PR успела
измениться, явно укажи, что новая голова ещё не проверена. Незавершённое ревью не записывай.

При `unchanged` не добавляй строку-дубль. Если запись этого прогона в PR отсутствует,
восстанови её из завершённой локальной записи с прежними временем и SHA: это не новое ревью.
Флаг `--no-pr-log` действует и в этом случае.

Тело запроса сериализуй JSON-библиотекой во временный файл и отправь через `gh api --input`:
PATCH существующего комментария или POST нового. Если PATCH вернул 403, создай новый журнал,
сохранив предыдущие строки. При неопределённом ответе сначала перечитай комментарии, чтобы
не продублировать принятую запись. Нет PR, `gh` или прав — сохрани локальный результат и
скажи в отчёте точную причину пропуска; не пропускай запись молча. Верни ссылку на журнал.

## 6. Запрошенные действия после отчёта

- `--comment` или явная просьба опубликовать — выполни [pr-comments](../pr-comments/SKILL.md).
- `--fix` или явная просьба исправить — выполни [apply-fixes](../apply-fixes/SKILL.md).
- Оба флага: сначала публикация проверенного коммита, затем правки.

После read-only ревью убери только созданный тобой чистый worktree без `--force`.
Если в нём появились изменения или применены исправления — сохрани его и сообщи путь.
Не удаляй чужие worktree. Ошибка GitHub не должна терять готовый локальный отчёт.
