# Review Kit для Codex

Проведи ревью и верни подтверждённые находки. Язык — язык запроса. Явные указания пользователя
и инструкции окружения приоритетнее этого навыка. Завершённый прогон записывается локально и
в журнал PR по правилам ниже. Ревью само по себе не разрешает менять код, публиковать подробные
замечания у строк, коммитить, пушить или одобрять PR.

Пути ниже относительны к каталогу этого `SKILL.md`, не к проверяемому проекту. Определи
абсолютный путь установленного пакета по пути навыка. `PLUGIN_ROOT` в примерах — корень
`review-kit`, на два уровня выше каталога этого навыка; это локальная переменная, а не обязательная
переменная окружения. Не ищи пакет в `.claude/` или в исходном репозитории автора.

## 1. Зафиксируй предмет проверки

Определи базу, SHA, рабочее дерево и порядок уборки по
[review-target.md](../references/review-target.md).
Прочитай [правила приватных артефактов](../../references/review-artifacts.md) для
`SNAPSHOT_FILE`, `REPORT_FILE`, `CI_FILE`; задай `PR_REPO` / `PR_NUMBER` из канонического PR.

Создай снимок **до** анализа и сохрани JSON во временный файл:

```bash
python3 "$PLUGIN_ROOT/scripts/review_snapshot.py" capture --repo "$REVIEW_ROOT" \
  --base "$BASE_SHA" --head "$HEAD_SHA" --target "$TARGET" --scope "$SCOPE"
```

`TARGET` — канонический URL PR или имя текущей ветки; `SCOPE` — `auto`, `all`, `min` либо
выбранные зоны через запятую. По умолчанию `auto`. `merge_base` в ответе — точка расхождения.
Для PR читай `git diff <merge_base> <head_sha>`; для текущего дерева —
`git diff <merge_base>` плюс untracked. Параметр `--rules <путь>` можно повторять для прочитанных
проектных руководств; относительные пути разрешаются от корня проверяемого проекта, файлы вне
проекта тоже подходят. `AGENTS.md`, `AGENTS.override.md` и `CLAUDE.md` проекта, включая
игнорируемые git, и глобальные инструкции Codex помощник учитывает сам.

## 2. Первый или повторный прогон

Прочитай [общую политику полного ревью](../../references/balanced-review.md): область по
кругам, влияние на старые файлы, план проверок, матрица безопасности, CI и решение о мерже.

Помощник читает только локальный журнал `review-kit-codex.jsonl` в общем git-каталоге.
Комментарии PR и старый журнал Claude не являются доказательством завершённого Codex-ревью.

Режим помощника задаёт доступное покрытие; правила его применения — в общей политике:

- `unchanged`: совпали снимок/правила/пакет/область.
- `followup`: совместимая история чистых деревьев; `increment` содержит свои коммиты/файлы
  и разрешения конфликтов, `base_changes` — изменения базы. Для подтверждения прочитанного
  списка при переиспользовании используй `base_changes_key`, возвращённый помощником.
- `first`: достоверного совместимого снимка нет, нужен анализ всего запрошенного diff.

## 3. Выбери зоны и прочитай общие чек-листы

Чек-листы общие с Claude Code. Загружай только выбранные документы и их предметные разделы:
границы зоны, ключевые принципы, чек-листы. Их YAML (`model`, `tools`, `effort`),
Claude Agent/Skill tool, подготовка, журнал и шаблоны вывода **не настраивают Codex**.
Запуск, инструменты, сравнение и отчёт определяет этот навык.

| Зона | Когда нужна | Общий документ |
|---|---|---|
| branch | изменена исполняемая логика | [Корректность](../../agents/agent-branch-reviewer.md) |
| security | внешний ввод, БД, сеть, файлы, секреты или персональные данные | [Безопасность](../../agents/agent-security-reviewer.md) |
| auth | вход, сессии, права, токены, деньги или чувствительные действия | [Доступ](../../agents/agent-auth-reviewer.md) |
| performance | изменены запросы, циклы по данным, списки или тяжёлый рендер | [Производительность](../../agents/agent-performance-reviewer.md) |
| design | затронут UI и есть применимые правила дизайна | [Дизайн](../../agents/agent-design-reviewer.md) |
| simplify | существенный объём или явное дублирование | [Упрощение](../../agents/agent-simplify.md) |

Security/auth выбирай при слабом признаке; performance/design — при явном. Маленькой правке
достаточно одного прохода. `all` включает все зоны, `min` — branch с явными рисками остальных,
`security,auth` — только перечисленные зоны. Неприменимые пункты не превращай в замечания.

Стек определяй по [detect-stack](../detect-stack/SKILL.md), по манифестам затронутых
приложений, а не всему монорепозиторию сразу. База и SHA уже зафиксированы в шаге 1:
обнаружение стека не должно подменять их. Прочитай подходящие картриджи:
[Yii2](../stack-yii2/SKILL.md), [Laravel](../stack-laravel/SKILL.md),
[Next.js](../stack-nextjs/SKILL.md), [React SPA](../stack-react-spa/SKILL.md),
[Expo/React Native](../stack-expo-rn/SKILL.md).
Legacy-код не наследует правила соседнего Yii2-приложения. Команды картриджа — подсказки:
применяй реальные настройки проекта. Проектные Resource-классы, model behaviors и прочие
явные контракты приоритетнее общих советов об API и массовых обновлениях.
Проверку словарей и ключей выполняй по [i18n-sync](../i18n-sync/SKILL.md) в режиме
`--check`: read-only ревью не разрешает менять локализацию.

Перед каждым новым анализом выбери модель и effort по
[общей политике](../../references/execution-routing.md), разделы «Решение по задаче»,
«Codex» и «Отчёт». При делегации выбирай настройки отдельно для каждой зоны и передавай
реальными параметрами инструмента запуска. Полный fork может не поддерживать overrides:
тогда используй свежий контекст с явной передачей задания и правил.

Если инструменты подагентов доступны и их применение разрешено текущим запросом и окружением,
делегируй независимые выбранные зоны read-only ревьюерам. Этот навык предусматривает такую
делегацию для содержательного ревью. Не используй имена Claude-агентов как типы Codex-агентов,
не переноси `opus` и его effort. При отсутствии делегации проверь зоны сам последовательно,
применяя общую политику исполнения и её ограничения.
В отчёте честно укажи способ проверки; не имитируй независимое подтверждение.
Каждому ревьюеру передай рабочий каталог, фиксированные SHA, diff, правила, состав зон и
ограничения проверок. Проверки запускает один ответственный, чтобы не дублировать их.

## 4. Проверь и сведи результат

Прочитай изменённые файлы и прямых вызывающих/потребителей. Замечание требует конкретного
сценария, последствия и подтверждения кодом. Отделяй дефекты этого изменения от прежних проблем
и необязательных предложений. Совпадение мнений само по себе не доказывает дефект.

Выполни проверки по [правилам команд](../../references/check-commands.md)
и общей политике полного ревью.

Одна проблема — одна находка. Отчёт содержит:

- предмет проверки, base/head SHA, стек, режим и выбранные зоны; для незакоммиченного —
  явно «рабочее дерево поверх `<head_sha>`», а не сам коммит;
- находки с приоритетом, файлом и точной строкой, сценарием и рекомендацией;
- все найденные необязательные предложения, механические и мелкие замечания — отдельно
  от блокирующего; не заменяй их счётчиком, они тоже передаются в `pr-comments`;
- старые замечания: подтверждено исправление / осталось / невозможно проверить;
- фактически выполненные проверки с результатами и ограничения;
- `impact`, краткий план проверок, таблицу безопасности и статус CI для точных head/base SHA;
- `МЕРЖИТЬ / МЕРЖИТЬ ПОСЛЕ <условие> / НЕ МЕРЖИТЬ`, исправленное с известными коммитами
  и порядок деплоя, если есть зависимость;
- запрошенные модель и effort по ролям, подтверждённые настройки или ограничения выбора;
- `NEEDS WORK` для критичного, `READY AFTER FIXES` для важных исправлений,
  `READY TO PR` при отсутствии обоих. Недостаток данных отрази явно, не выдавай уверенный допуск.

Сохрани итог во временный JSON: `verdict` (один из трёх выше), `findings` (массив находок),
`open` (массив незакрытых важных/критичных замечаний), `checks` (массив команд и результатов).
В `findings` сохрани все уникальные замечания, включая механические, мелкие и предложения;
`open` остаётся только списком важных/критичных и не заменяет полный отчёт для публикации.
Добавь `zones`, `stack`, `summary`, `execution` (выбор модели/effort по ролям и ограничения)
и `limitations`, чтобы повторить контекст и ограничения сохранённого результата.
Добавь `impact`, `check_plan`, `security_coverage`, `ci`, `merge_decision`, `conditions`,
`analysis_reused` по [общей политике](../../references/balanced-review.md).
Номер `analysis_round` назначает помощник записи.
Строки и переводы строк сериализуй JSON-библиотекой, не shell-интерполяцией.

```bash
python3 "$PLUGIN_ROOT/scripts/review_snapshot.py" record --repo "$REVIEW_ROOT" \
  --snapshot "$SNAPSHOT_FILE" --report "$REPORT_FILE"
```

Помощник откажется записывать результат, если код или правила изменились во время ревью.
Тогда обозначь границу проверенного, а не сохраняй устаревший вердикт. Журнал локальный;
его отсутствие на другой машине означает первый прогон. История в PR дополняет этот журнал,
но не заменяет снимок для автоматического повторного использования результата.

## 6. Запрошенные действия после отчёта

- `--comment` или явная просьба опубликовать — выполни [pr-comments](../pr-comments/SKILL.md):
  весь список, важное inline, остальное блоком `suggestion` в body review.
- `--fix` или явная просьба исправить — выполни [apply-fixes](../apply-fixes/SKILL.md).
  По умолчанию весь готовый список, включая предложения/упрощения; вопрос только при
  существенной неоднозначности. Явные исключения пользователя сохраняются.
  Включая ответы на исправленные inline-комментарии и resolve решённых в PR обсуждений.
  Для падения CI соблюдай потолок трёх попыток и остановку без нового подтверждения
  по общей политике; после правок проверь затронутые связи. Push требует своего основания.
- Оба флага: сначала публикация проверенного коммита, затем правки.

Уборка — по [review-target.md](../references/review-target.md).
Ошибка GitHub не должна терять готовый локальный отчёт.
