# Ship в Codex

Доведи выбранные изменения до опубликованной ветки и PR. Явный вызов `ship` разрешает
commit, push и создание/обновление PR в рамках задачи; не спрашивай это повторно.
При автоматическом выборе навыка разрешения определяет реальный запрос пользователя:
«проверь» не разрешает отправку. Ограничение «только подготовь» или «без push» сохраняется.
Инструкции пользователя и окружения приоритетнее этих правил.

## 1. Репозиторий и ветка

Прочитай правила проекта, шаблон PR, соглашения о ветках/коммитах и запретные файлы.
Выполни [detect-stack](../detect-stack/SKILL.md), проверь `git status --short --branch`,
`git remote -v`, текущую ветку, индекс, рабочее дерево и последние коммиты. Проверь `gh`
и авторизацию до внешних действий; недоступный GitHub не повод потерять локальную работу.

Определи базовый репозиторий/ветку и remote для push. Для существующего PR сохрани его
фактическую базу и head repository: в форке push идёт в форк, PR — в базовый репозиторий.
Не угадывай remote при нескольких равноправных вариантах.

Никогда не коммить и не пушь в базовую ветку. Если открыта база, создай отдельную ветку
из смысла задачи: по правилам проекта, по умолчанию `darkezar/<краткое-имя>`.
Запроси название только когда его нельзя вывести из задачи. При detached HEAD создай
именованную ветку на текущем коммите. Не переключайся с потерей изменений и не используй
автоматические stash/reset/clean. Уже существующую подходящую ветку не создавай заново.

## 2. Границы отправки и проверки

Просмотри полный diff ветки от merge-base, staged, unstaged и релевантные untracked.
Определи, что относится к задаче. Сохрани чужие/несвязанные правки, включая индекс.
Если в индексе есть несвязанные изменения, не включай их в коммит и не сбрасывай их молча:
используй изолированное индексирование согласованных путей либо уточни пересечение,
которое невозможно безопасно разделить. Ничего не добавляй через `git add .` или `-A`.

Проверь **весь отправляемый diff**, включая уже готовые коммиты, на секреты, локальные
настройки, зависимости и сборочные артефакты. `.env`, credentials, приватные ключи,
keystore и service accounts не отправляй; учитывай правила проекта для намеренно
версионируемых шаблонов и сгенерированных файлов. Секретные значения не печатай в отчёте.

Команды типов, линта и релевантных тестов найди в инструкциях и конфигурации проекта.
Если доступен `detect-tooling`, используй его; это необязательная зависимость.
Иначе проверь Makefile/justfile, package/composer scripts, CI, контейнеры и картриджи
из detect-stack. Проверь существование бинаря и читай тело скрипта. Запускай проверяющие
формы в правильном каталоге, без автофиксов/миграций и автоматической установки пакетов.
Проверь `git diff --check` и индекс. Если проверки меняли дерево — пересмотри diff.

Ошибки своей правки исправляй в разрешённом объёме и повтори затронутые проверки.
При оставшихся ошибках сообщи команду и причину. Не коммить и не отправляй известное
падение молча: для продолжения нужен уже заданный пользователем допуск либо его решение.
Отсутствие среды обозначь как «не запускалось»; оно не превращается в passed.
Полный `agent-full-review` выполняй, если запрошен или требуется правилами проекта;
`ship` не утверждает, что ревью уже было.

## 3. Коммит

Добавь конкретные согласованные пути и проверь фактический staged diff перед коммитом.
Для целых выбранных файлов при постороннем staged используй `git commit --only -- <пути>`:
он исключает постороннее из коммита и обновляет отправленные записи исходного индекса.
Для частично выбранных файлов индексируй только согласованные фрагменты. Если необходим
отдельный индекс, после коммита перенеси в исходный индекс только отправленные изменения
относительно нового HEAD, сохранив несвязанные staged-фрагменты. Не оставляй весь старый
индекс неизменным при сдвиге HEAD: старые blobs станут staged-откатом отправленного кода.
Сверь оставшийся staged diff с исходными несвязанными правками; отправленные изменения
не должны появляться в нём обратным патчем. Если изменений для нового
коммита нет, но ветка содержит готовые коммиты, переходи к push; пустой коммит не нужен.
Если нет ни правок, ни отличий от базы, сообщи, что отправлять нечего.

Сообщение: английский title до 70 символов, префикс по смыслу (`feat:`, `fix:`,
`refactor:`, `style:`, `chore:`), при необходимости body. Правила проекта приоритетнее.
Не используй amend и `--no-verify` без соответствующего разрешения/обоснованного допуска.
Падение pre-commit hook не обходи автоматически. После коммита проверь SHA, ветку и
оставшиеся правки; не приписывай коммиту проверки другого состояния.

## 4. Push и Pull Request

Отправь текущую feature-ветку обычным push в согласованный remote, установив upstream
при первом push. Не используй force и не переписывай историю для обхода отказа.
При non-fast-forward сначала выясни расхождение; не меняй чужую историю автоматически.
Если ответ push неопределённый, проверь SHA remote-ветки перед повторной отправкой.

Найди открытый PR именно для того же head repository и ветки. Существующий обнови,
новый создай только при его отсутствии. Закрытый/слитый PR не переоткрывай автоматически.
Перед созданием проверь все коммиты и полный diff до текущего HEAD относительно
фактической базы. В `gh pr create` явно задай базу и голову, учитывая форк.

По умолчанию title — имя ветки как в Claude-команде; явный title пользователя или
шаблон проекта приоритетнее. Body на русском, краткий и понятный ревьюеру:

- «Что делает» и «Почему»; для багфикса — «Симптом» и «Причина»;
- «Что сделано»: суть итогового решения;
- «Как проверить»: сценарий и фактически выполненные проверки с ограничениями;
- «Файлы»: значимые модули и их роль, косметика одной строкой.

Масштаб описания соразмерен изменению, обычно до 30–60 строк, без вложенных списков
и пересказа коммитов. Используй проектный шаблон, если он есть. Для UI укажи реально
проверенное соответствие дизайну. Не добавляй подпись Claude Code. Существующее описание
обновляй по итоговой реализации, сохраняя содержательный контекст и ссылки пользователя.
Запиши точное тело во временный UTF-8 файл и передай через `--body-file`; не собирай
многострочный body shell-интерполяцией.

При таймауте создания сначала найди PR повторно: не создавай дубликат вслепую.
После создания **или работы с существующим PR** прикрепи его к текущему чату штатным
инструментом приложения, если он доступен. Это локальное действие приложения, не
публикация review. Не одобряй и не сливай PR, не меняй reviewers/labels без запроса.

Верни URL PR, имя ветки, SHA коммита, результаты проверок и оставшиеся локальные правки.
Если выполнение остановилось, укажи точный завершённый этап и причину; не называй
локальный коммит опубликованным. Повторный вызов продолжает с достигнутого состояния.
