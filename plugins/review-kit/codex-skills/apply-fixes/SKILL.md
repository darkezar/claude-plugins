# Исправления после ревью в Codex

Нужны готовый отчёт либо inline-замечания указанного PR и команда пользователя исправлять.
Прочитай [общую политику исправлений](../../references/fix-scope.md): весь список по
умолчанию, границы запроса, критерий неоднозначности и подтверждение результата.
Явные инструкции пользователя и окружения приоритетнее навыка. Предметные инструкции
[agent-fixer](../../agents/agent-fixer.md) — справочник, его YAML не настраивает Codex.

Перед каждой партией выбери модель и effort по
[политике исполнения](../../references/execution-routing.md), разделы «Решение по задаче»,
«Codex» и «Отчёт». Сохраняй заданные пользователем решения/настройки. Для поддерживаемых
per-call overrides навык предусматривает последовательную делегацию одному исполнителю:
передай все однозначные пункты партии, включая предложения, состояние, правила, команды
и comment ID; дождись результата. При недоступной делегации работай сам только на модели
допустимого класса и с effort от `medium`; иначе сообщи ограничение по общей политике.

1. Проверь ветку/коммит и дерево относительно отчёта. В отдельном worktree работай там,
   сообщи путь. Перечитай изменившиеся после ревью места, сохрани правки/индекс пользователя.
   Само наличие несвязанных правок не требует остановки; неразделимое пересечение требует
   уточнения намерения. Для PR прочитай [ответы и resolve](../../references/fix-review-threads.md),
   дочитай все страницы threads/comments и свяжи находки со всеми исходными comment ID.
2. Возьми все уникальные пункты полного отчёта, не только `open`: обязательные, механические,
   мелкие, предложения, упрощения, необязательные оптимизации и старое автоматическое
   «Отложено по умолчанию». Явное исключение пользователя/ограничение категорий сохраняется.
   Исправляй все актуальные однозначные пункты, включая логику, безопасность и архитектуру,
   без дополнительного подтверждения. Для локализации используй
   [i18n-sync](../i18n-sync/SKILL.md) в пределах замечаний; переводы не выдумывай.
3. Спрашивай только при существенной неоднозначности по общей политике: конкретный сценарий,
   существенно разные результаты, последствия и рекомендация. Обычные детали реализации
   выбирай по проекту, заданное решение повторно не согласовывай. До ответа не правь зависимые
   места, продолжай независимые пункты. Необязательность сама по себе не повод отложить.
4. Один писатель, последовательные правки; модель/effort пересматривай по реальной сложности.
   Исполнитель возвращает статусы всех замечаний и все comment ID. Ответы/resolve ведёт
   координатор, чтобы не дублировать публикации.
5. Найди реальные команды проверок в проекте, запусти релевантные синтаксические и
   поведенческие проверки одним ответственным. Для дефекта поведения — регрессионное
   подтверждение до/после, когда выполнимо; недоступное обозначь ограничением. Для механики
   и эквивалентного упрощения не добавляй тесты, повторяющие реализацию. Просмотри весь diff,
   включая новые файлы, и `git diff --check`.
6. По [общей процедуре PR](../../references/fix-review-threads.md) ответь на каждый исправленный
   inline, включая дубли/частичные правки, с фактическими проверками. Локальное/частичное
   состояние обозначь прямо. Resolve — только целиком решённых в опубликованном PR threads,
   после проверки новых сообщений, головы, прав и `isResolved`. Сверь весь `reply_map`.
   `--comment` не нужен; явный запрет GitHub-действий сохраняется.

В результате каждый исходный пункт имеет статус из общей политики, включая необязательное.
Укажи файлы, исправленное/оставшееся с причинами, проверки/ограничения, выбор исполнения,
worktree, `reply_map`, ответы N из всех исправленных comment ID и закрытые/оставшиеся threads.
Коммит, push и публикация новых находок требуют своего основания; не переспрашивай уже данное
разрешение. После разрешённого push заверши ожидающие ответы/resolve. Исправления не заменяют
повторную проверку затронутого кода и его влияния по [agent-full-review](../agent-full-review/SKILL.md).
