# Археология репозитория

История отвечает на вопрос, на который не отвечает текущий код: **когда это стало неверным
и что изменилось вокруг**.

## Найти, когда появился или исчез код

`-S` ищет коммиты, где **изменилось количество вхождений** строки. Лучший способ найти,
где что-то зародилось.

```bash
git log -S'is_test' --oneline -- backend/            # где появлялось/исчезало
git log -S'is_test' -p -- backend/app/Models/        # сразу с диффами
```

`-G` ищет коммиты, где **менялись строки, подходящие под регулярку** — шире, чем `-S`.

```bash
git log -G'charge_id\s*(===|==|IS)\s*NULL' --oneline
```

Разница существенная: `-S` покажет введение и удаление, `-G` — ещё и любую правку рядом.
Начинай с `-S`, он тише.

## Проследить эволюцию куска

```bash
git log -L :scopeOnTestContainer:backend/app/Models/Booking.php   # по имени функции
git log -L 40,80:path/to/file                                     # по диапазону строк
```

Это самый быстрый способ увидеть, как конкретная функция дожила до текущего вида.

## Кто и когда трогал строку

```bash
git blame -w -C -C path/to/file          # -w игнорирует пробелы, -C ищет перенос из других файлов
git blame -L 40,60 path/to/file
```

**Осторожно с выводами.** `blame` показывает, кто коснулся строки **последним**, а не кто
внёс смысл. Массовое переформатирование или переезд файла делают его бесполезным без `-w -C`.
Если в репозитории есть `.git-blame-ignore-revs`, подключи: `--ignore-revs-file`.

## Найти ломающий коммит автоматически

Когда воспроизведение можно выразить командой — `bisect` находит коммит за логарифм шагов.

```bash
git bisect start <плохой> <хороший>
git bisect run <команда, возвращающая 0 если хорошо>
git bisect reset
```

Команда должна быть **быстрой и надёжной**. Если тест мигает, bisect уверенно приведёт не туда.
Когда прогон невозможен (нужен контейнер, база, ручная проверка) — не имитируй bisect
догадками, скажи об этом и ищи по `-S`/`-G`.

## Сопоставить две линии времени

Самый ценный приём, и его не заменяет ни один одиночный поиск. Многие баги устроены так:
**код был верен, когда его писали, а потом рядом появилось изменение, которое ввело второй
законный смысл для того же условия — и старый код об этом не узнал.**

Практически:

1. Найди, когда написали подозреваемый код и **какое допущение** он делал (`-S`, сообщение коммита).
2. Найди, когда появилась сущность, которая это допущение нарушает.
3. Сравни даты. Если вторая позже — почти наверняка причина здесь.
4. Проверь решающим тестом: упоминается ли новая сущность в старом коде и **в его тестах**.
   Отсутствие упоминания — это и есть доказательство, что связь не заметили.

```bash
git log --oneline --since='6 months ago' -- <файл-подозреваемый> <файл-новой-сущности>
git log -S'<имя новой сущности>' --oneline -- <каталог старого кода>   # пусто = связь не увидели
```

## Найти собратьев

Найдя причину, **не останавливайся на одном месте**. То же допущение обычно сделано ещё
в двух-трёх местах, написанных тем же человеком в то же время.

```bash
git log -S'<ключевое условие>' --oneline --all      # где ещё встречается
grep -rn '<ключевое условие>' --include='*.php' .
```

Отдельно проверь обратное: нет ли места, где ту же ловушку уже обошли — тогда там есть готовый
образец решения, согласованный с проектом.

## Дисциплина

- **Сначала воспроизведение, потом история.** Без него ты подтверждаешь догадку, а не находишь причину.
- **Различай спусковой крючок и причину.** «Пользователь нажал кнопку» — крючок. Причина — почему
  нажатие приводит к такому исходу.
- **Не останавливайся на первом правдоподобном.** Первое найденное совпадение по времени бывает
  соседним изменением, а не виновником.
- **Отсутствие следа — тоже улика.** Если в старом коде и его тестах ни разу не упомянута новая
  сущность, это сильное свидетельство, что о ней не знали.
