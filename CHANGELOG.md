# Изменения

Версия плагина живёт в его `plugins/<имя>/.claude-plugin/plugin.json`. Правишь плагин —
подними версию, иначе у тех, кто ставил с GitHub, `/plugin update` не подхватит изменения.
Своей копии, подключённой путём (`directory`), это не касается: она грузится прямо из
рабочего дерева, версия ей не нужна (проверено опытом на Claude Code 2.1.283).

## workflow-gate

### 0.2.2
- Раздел «Обновление» описывал один порядок на оба случая и в части локального каталога был
  неверен. Теперь случая два, по типу подключения: каталог, подключённый путём (`directory`),
  грузится прямо из рабочего дерева — правка видна после перезапуска сессии, версию поднимать
  не нужно; каталог, подключённый именем (`github`), требует подъёма версии, пуша и
  `/plugin marketplace update` + `/plugin update` у пользователя.
- Проверено опытом, а не рассуждением: в описание `/upgrade-check` в рабочем дереве внесена
  строка-метка без подъёма версии и без касания кэша, после чего отдельный процесс `claude -p`
  процитировал именно её. Подтверждается и устройством: у каталога `darkezar` в
  `known_marketplaces.json` стоит `source: directory`, а `installLocation` указывает на сам
  репозиторий, а не на копию.
- Прежнее утверждение («правки не доезжают даже при локальном каталоге») разошлось с разделом
  «Кэш врёт при локальной отладке» в главном README, и правым оказался он.

### 0.2.1

  сам, разрешения не спрашивай», ни отмены встроенной осторожности инструмента Workflow,

### 0.2.0
- Судья зовётся на **каждый** запуск, и его вердикт окончателен. Раньше явная просьба или
  вызов слэш-команды открывали ворота сразу, без проверки.
- Причина не в недоверии к просьбе, а в том, как она ловилась: признак искался в трёх
  последних сообщениях, поэтому «разверни агентов», сказанное для одной задачи, открывало
  ворота и для следующей, уже другой.
- Признаки просьбы теперь уходят судье как сведения: он видит «явная просьба — да/нет» и
  «слэш-команда — да/нет» и взвешивает их вместе с существом задачи. Отклонить прямую
  просьбу он вправе.
- Единственный обход — `/workflow-pass`: при открытом пропуске судью не зовут вовсе.
- При отказе на явную просьбу Клоду велено сказать об этом первой строкой ответа — иначе
  пользователь не поймёт, почему агентов нет.
- В журнал добавлена пометка, была ли просьба: `(просьба)`, `(просьба+команда)`,
  `(без просьбы)`. Нужна, чтобы видеть, как часто судья идёт против пользователя.

### 0.1.1
- В README плагина — раздел «Обновление». Установка копирует плагин в
  `~/.claude/plugins/cache/<каталог>/<плагин>/<версия>/`, и правки в репозитории туда сами
  не доезжают даже при локальном каталоге: без подъёма версии `/plugin update` отвечает
  «already at the latest version» и ничего не делает. Проверено на 2.1.278.
  **Про локальный каталог утверждение неверно — опровергнуто в 0.2.2.**

### 0.1.0
- Ворота на инструмент `Workflow`. Режим ultracode велит разворачивать фан-аут почти на любую
  задачу, и именно оттуда берётся основная часть расхода: разбор трат показал, что три
  четверти ушло на агентов, которых никто не просил. Плагин возвращает это решение человеку.
- Разрешено без вопросов: явная просьба в последних сообщениях, вызов слэш-команды (её скилл
  решает сам), открытый временный пропуск `~/.claude/workflow-allow`.
- Всё остальное уходит судье — отдельной дешёвой сессии `claude -p`, которая видит последние
  сообщения пользователя и паспорт запуска: имя, описание, число фаз и вызовов `agent()`.
  Асимметрия зашита в промпт: ошибочный отказ стоит немного, ошибочное разрешение — вдесятеро
  дороже. Судья недоступен или ответил невнятно — отказ.
- Отказ ничего не ломает: это `deny` с объяснением, задача делается обычным способом. Ночные
  прогоны из-за ворот не встают.
- `/workflow-pass <часов>` — временный пропуск, закрывается сам. Без аргумента 2 часа.
- Каждое решение пишется строкой в `~/.claude/workflow-guard.log`.
- Переменные: `WORKFLOW_GATE_JUDGE=off` (не звать судью вовсе), `WORKFLOW_JUDGE_MODEL`,
  `WORKFLOW_JUDGE_TIMEOUT`.
- Текст правила для своего `CLAUDE.md` лежит в README плагина: плагин не может дописать в чужой
  файл, а без этого текста Клод продолжает пытаться развернуть агентов и ловить отказ.

## review-kit

### 0.5.0
- Тимлид, ревьюивший ветку программиста, не получал записи в журнал PR. Возможных причин в тексте
  скилла было три, все закрыты:
  - описание `--no-pr-log` («нужен, когда PR чужой») читалось как разрешение пропустить запись
    по авторству. Теперь прямо сказано: чей PR — не важно, не писать решает только сам аргумент;
  - PR искался только по имени текущей ветки (`gh pr view`). Ветка, взятая под другим именем, в
    worktree или с отсоединённым `HEAD` давала «PR нет». Теперь есть запасной поиск по коммиту,
    и номер или ссылку PR можно передать аргументом;
  - если комментарий-журнал создал программист, а правка чужого комментария отказала, запись
    терялась. Теперь в таком случае создаётся новый журнал со всей таблицей, и читается последний.
- Журнал в PR читается с `--paginate`. Без него приходили только первые 30 комментариев, а в
  обсуждаемых PR программистов их больше — журнал не находился, и прогон считался первым.
- `agent-full-review <номер PR>` ревьюит ветку этого PR: переключается на неё при чистом дереве и
  пишет журнал в этот PR. При отсоединённом `HEAD` ключ в локальном журнале — `pr-<номер>`.
- Пропуск записи в PR теперь объясняется в отчёте: какой шаг не сработал и что ответил `gh`.
- Новая команда `/pr-comments`: выкладывает отчёт ревью в PR комментариями у строк, одним ревью
  на GitHub. Что вне диффа, уходит в текст ревью. Повторный запуск не дублирует уже выложенное.
  Ревью всегда уходит как `COMMENT`: одобрить или вернуть PR решает человек. То же после отчёта
  делает аргумент `agent-full-review --comment`.
- Если PR чужой и замечания есть, `agent-full-review` в конце отчёта напоминает про `/pr-comments`.

### 0.4.0
- `agent-full-review` сам решает, какой это прогон, — аргументы для этого больше не нужны.
  По журналу прогонов: **первый** классифицирует весь дифф, как раньше; **повторный** смотрит
  только прирост с прошлого раза (свои коммиты ветки, без слияний с базовой) и обычно зовёт
  одного ревьюера кода — проверить, что замечания закрыты и правки ничего не сломали рядом;
  **без изменений** (коммит уже проверен) не запускает никого. Если прирост — только тесты и
  комментарии, агентов не будет вовсе; если правки переписали больше трети ветки — полный состав.
- Причина — цена: прежнее правило «после NEEDS WORK — весь дифф заново» гоняло трёх агентов по
  всей ветке на каждом круге. На одной ветке три круга ревью с правками обошлись примерно в
  4 млн токенов агентов, а отдача падала: 18 → 15 → 10 замечаний, критичных 1 → 1 → 0.
- `simplify` в повторном прогоне не запускается: упрощение мерж не блокирует, а каждая внесённая
  «чистка» — новый код под ревью.
- Effort агентам задаётся явно: `high` для первого прогона по деньгам, правам, входу и
  необратимым действиям, иначе `medium`; повторный — `medium`. Без этого агенты брали
  настройку сессии, вплоть до максимальной.
- Новый вердикт `READY AFTER FIXES`: критичного нет, есть «важное» — внести правки без полного
  повторного ревью. `NEEDS WORK` теперь только при критичном замечании или `FAIL` у
  безопасности или авторизации; раньше его давал любой `REQUEST CHANGES`, и вердикт не отличал
  блокер от мелочи. В конце отчёта — строка «следующий шаг».
- В журнале прогона новые поля: `mode` (`first`/`followup`) и `open` — незакрытые «критично» и
  «важно». По ним повторный прогон проверяет, что закрыто.
- `apply-fixes`: третья стопка «отложено по умолчанию». Предложения ревьюера упрощений и
  необязательные оптимизации больше не превращаются в развилки — каждое одной строкой в отчёте,
  забрать можно словами. Механическая часть упрощений по-прежнему применяется. В конце отчёта —
  следующий шаг: снова `/agent-full-review`, который сам будет повторным.

### 0.3.2
- Журнал прогонов в `agent-full-review`. Ревью одной ветки идёт из разных сессий, машин и
  worktree, и без следа невозможно ответить на единственный важный вопрос — проверялось ли то,
  что в ветке сейчас. Число прогонов само по себе ничего не значит: три ревью по устаревшему
  коду хуже одного по текущему.
- Пишется в два места. Локально — строка JSON в `$(git rev-parse --git-common-dir)/review-log.jsonl`:
  служебный каталог git, поэтому не попадает в дифф, не требует `.gitignore` и общий для всех
  worktree репозитория. В PR — один обновляемый комментарий с маркером `<!-- review-kit:log -->`,
  и это единственное место, которое переживает смену машины и читается без Claude.
- Прогон стал инкрементальным: если по ветке уже было ревью, состав агентов классифицируется по
  изменениям поверх проверенного коммита, а не по всему диффу. Зоны при этом сужаются, но не
  выключаются — в отчёте пишется, что зона проверена на коммите `<sha>` и с тех пор не менялась.
  Исключение — прошлый вердикт `NEEDS WORK`: тогда состав берётся по всему диффу.
- Если `HEAD` совпадает с последним прогоном, скилл говорит об этом до запуска агентов и
  спрашивает, точно ли повторять.
- Аргумент `--no-pr-log` — не писать в PR, когда он чужой или публичный.

### 0.3.1
- Агенты объявляли инструменты ключом `allowed-tools` — он работает в командах и скиллах, но
  в файле агента игнорируется. Все семеро получали не заявленный набор, а полный доступ.
  Заменено на `tools`. Побочно: `tools` не принимает скоупы, поэтому прежнее сужение до
  `Bash(git diff)` и подобных недостижимо через фронтматтер — ревьюеры получают `Bash` целиком.
- Клапан «Замечено попутно» — находка в чужой зоне пишется одной строкой, без разворачивания —
  был только у `simplify`. Теперь у всех ревьюеров, вместе с причиной: агенты идут параллельно
  и не видят друг друга, поэтому одна проблема приезжала в отчёт четырьмя пересказами.
  Обнаружено на боевом прогоне: `->first()` без сортировки расписали все пять запущенных агентов.
- Сведение дублей в оркестраторе: запись живёт в секции владельца зоны, а не того, кто написал

- Оркестратор передаёт агентам, чего в этом окружении не запустить (нет рантайма, контейнеров,

## git-kit

### 0.1.0
- `/git-state` и скилл `git-inventory`. Состояние репозитория для работы без git-интерфейса:
  текущая ветка показывается всегда, даже когда всё чисто, — увидеть её больше неоткуда.
- Находки отсортированы по риску потери, а не по типу объекта: «только здесь» (незакоммиченное,
  ветки без upstream, стеши, worktree, detached HEAD) → «мешает» → «мусор».
- Разобраны ловушки, на которых обычно врёт ручная проверка: `git branch --merged` не видит
  squash-merge (нужен `git cherry`), ветка без upstream и ветка с `[gone]` — противоположные
  случаи, неотслеживаемые файлы невидимы для `git diff`, стеш не принадлежит ветке и не виден
  нигде, кроме `git stash list`.
- Действия только по подтверждению. Деструктивное (`reset --hard`, `clean`, `stash drop`,
  `branch -D`, `push --force`) не выполняется по своей инициативе никогда: команда существует
  ради сохранности работы и не имеет права её терять.

## explain-kit

### 0.1.0
- `/explain` и скилл `plain-language`. Берёт технический отчёт — последний в сессии, текст,
  файл или PR по номеру — и пересказывает так, чтобы по нему можно было принять решение.
- По каждому пункту: что не так двумя строками, конкретный случай «почему это плохо»,
  2–4 варианта таблицей с ценой и с тем, чего каждый **не** решает, и рекомендация с причиной
  из обстоятельств этого проекта. Последний вариант всегда «не чинить сейчас» — с честным риском.
- Сортировка не по ярлыку из отчёта, а по последствию: деньги и потеря данных → сломается
  у пользователя → будет тормозить → вкусовщина. Последняя очередь в разбор не идёт вовсе,
  ей место в «можно не чинить».
- Бюджет краткости соблюдается буквально: заголовок 5–7 слов без единого термина, «что не так»
  максимум две строки, один пример вместо трёх, больше семи пунктов — группировать.
  Длинный пересказ длинного отчёта не помогает никому.
- Примеры проверяются по коду. Если проверить нельзя — так и написано; если проверка показала,
  что проблемы нет, — это отдельный пункт. Переведённая на простой язык ошибка звучит
  убедительнее оригинала, поэтому молча её проносить нельзя.
- Не чинит, не ищет новых проблем и не меняет серьёзность ни в одну сторону. Не согласен
  с исходным отчётом — говорит явно, а не переставляет ярлыки.
- Формат развилки общий с `apply-fixes`, чтобы разбор из `/explain` можно было отдать в починку
  без пересборки.
