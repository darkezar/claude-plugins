# claude-plugins

Личный каталог плагинов Claude Code.

**[Памятка](CHEATSHEET.md)** — что набирать и когда. **[Изменения](CHANGELOG.md)** — что менялось.
Ниже — как это устроено.

| Плагин | Назначение |
|---|---|
| **review-kit** | Ревью-агенты с чек-листами под стек проекта |
| **tooling-kit** | Находит, как в проекте реально запускаются тесты и линтеры: `/test`, `/lint`, `/typecheck`, `/fmt` |
| **context-kit** | Создаёт и поддерживает `CLAUDE.md`: `/context-init`, `/context-refresh` |
| **debug-kit** | Разбор бага от симптома до причины через историю репозитория: `/debug` |
| **upgrade-kit** | Инвентаризация зависимостей и план обновления: `/upgrade-check` |

review-kit использует tooling-kit, если тот установлен: агенты берут команды у него, а не угадывают.

Общий набор ревью-агентов и команд для всех проектов. Ставится один раз, работает везде —
копировать `.claude/` из проекта в проект больше не нужно.

Чек-листы разделены на три слоя: универсальный (в агентах), стековый (картриджи `stack-*`)
и доменный (остаётся в `CLAUDE.md` конкретного проекта).

## Установка

```bash
/plugin marketplace add /srv/projects/claude-plugins
/plugin install review-kit@darkezar
```

Позже, когда репозиторий уедет на GitHub:

```bash
/plugin marketplace add darkezar/claude-plugins
/plugin install review-kit@darkezar
```

Управление — `/plugin`: список, включение и выключение, обновление.

## Что набирать

### Основное

| Команда | Что делает |
|---|---|
| **`/agent-full-review`** | **Главное.** Классифицирует дифф, выбирает нужных ревьюеров, гоняет параллельно, сводит в один отчёт. Это то, что запускают перед PR |
| `/ship` | Ветка → проверки → коммит → push → Pull Request |
| `/test` · `/lint` · `/typecheck` · `/fmt` | Из **tooling-kit**: запускают то, что реально настроено в проекте |

Аргументы к первой: `all` — все шестеро принудительно, `min` — только код-ревью,
`security,auth` — ровно перечисленные, `--fix` — применить механические замечания после отчёта.

### Точечно, когда нужен один ревьюер

`/security-review` · `/auth-review` · `/performance-review` · `/design-review` ·
`/simplify-review` · `/branch-review`

### Остальное

| Команда | Что делает |
|---|---|
| `/review` | Ревью одним проходом, без агентов — быстро и дёшево, но поверхностнее |
| `/apply-fixes` | Применить механическую часть замечаний к дереву (после ревью, не вместо) |
| `/i18n-sync` | Сверка и починка словарей локализации |
| `/debug` | Из **debug-kit**: симптом → воспроизведение → причина, с разбором по истории |
| `/upgrade-check` | Из **upgrade-kit**: что отстало, что без поддержки, план по шагам |
| `/context-init` · `/context-refresh` | Из **context-kit**: собрать `CLAUDE.md` · сверить его с реальностью |
| `/detect-stack` · `/detect-tooling` | Служебные: базовая ветка и стек · точки входа тулинга |

**Починка.** Ревьюеры read-only — у них нет `Edit`/`Write`, и это намеренно: правящий ревьюер
оценивает собственную работу, а шесть параллельных писателей конфликтуют в одном дереве.
Правки применяет отдельный `agent-fixer` после отчёта, последовательно.

Механическое — локализация, токены темы, устаревшие описания, мёртвый код, форматирование —
применяется сразу: там правильный ответ один.

Всё остальное превращается в **развилку**. По каждому замечанию показывается: в чём проблема,
конкретный сценарий как она стреляет, 2–4 варианта с последствиями и тем, что каждый **не**
решает, и рекомендация с обоснованием из контекста именно этого проекта. Дальше решаешь ты,
а агент реализует выбранное — вместе с тестом, который падает до правки и проходит после.
Молча выбрать за тебя он не может: тихо неверно закрытая дыра хуже незакрытой, потому что
с неё снимается внимание.

Запуск: `/agent-full-review --fix` или `/apply-fixes`.

**Агенты** — по одному на роль: `agent-branch-reviewer`, `agent-security-reviewer`,
`agent-simplify`, `agent-design-reviewer`, `agent-performance-reviewer`, `agent-auth-reviewer`.

## Как это работает

`agent-full-review` определяет базовую ветку (`main`, `master`, `develop` — по remote, а не
хардкодом), детектит стек по файлам-маркерам, **решает, какие ревьюеры вообще нужны**, и
запускает только их — параллельно.

Фиксированного набора нет: ни один агент не включается автоматически. Оркестратор сначала
классифицирует дифф (характер правки, затронутые слои, пересекается ли граница доверия, объём),
затем по каждому агенту принимает решение и обосновывает его одной строкой в отчёте. Ревью
одного PHP-класса не потянет за собой дизайн-ревьюера, а правка цвета кнопки — проверку индексов.

Запас несимметричен: **security** и **auth** включаются по слабому признаку (пропущенная дыра
дороже лишнего прогона), **design** и **performance** — только по явному, **simplify** — по
объёму диффа. На тривиальной правке фан-аут не разворачивается вовсе.

Аргументы: `all` / `full` — все шестеро; `min` / `core` — только код-ревью; `security,auth` —
ровно перечисленные.

### Разведённые зоны

Каждый агент отвечает за свою тему и не лезет в чужую, иначе одно замечание приезжало бы в отчёт
по четыре раза.

| Зона | Агент |
|---|---|
| Типы, паттерны, архитектура, тесты | branch |
| Уязвимости, секреты, инъекции | security |
| Права, сессии, токены, IDOR | auth |
| Ре-рендеры, списки, N+1, индексы, бандл | performance |
| Токены темы, примитивы, локализация | design |
| Дублирование, сложность, мёртвый код | simplify |

Если агент не запускался ради экономии, его зону **добирает** ближайший из запущенных — по верхам,
с пометкой добора (`auth` → `security` → `branch`). Если же агент пропущен потому, что его темы
в диффе просто нет, добор не назначается: покрывать нечего. Поэтому оркестратор передаёт каждому
агенту состав прогона и причину пропуска.

### Картриджи стека

Картридж — это три таблицы для конкретного стека: команды тулинга, триггеры условных ревьюеров
и привязки универсального чек-листа к API этого фреймворка.

Готовы: `stack-laravel`, `stack-yii2`, `stack-nextjs`, `stack-react-spa`, `stack-expo-rn`.

Стеков может быть активно несколько одновременно — в монорепо обычно фронт плюс бэк.

**Добавить новый плагин:** создай `plugins/<имя>/` с тем же устройством и допиши его в
`.claude-plugin/marketplace.json`. Плагины ставятся и выключаются независимо.

**Добавить новый стек:** создай `plugins/review-kit/skills/stack-<имя>/SKILL.md` по образцу
существующего и допиши строку в таблицу детекта в `skills/detect-stack/SKILL.md`. Агентов
трогать не нужно.

## Что остаётся в проекте

В `CLAUDE.md` каждого проекта — то, что не выводится из стека:

- доменные инварианты («сервер — единственный авторитет по деньгам», «дверь открывает только сервер»);
- локальные конвенции и запреты;
- префикс веток, если он отличается от `darkezar/`;
- дополнительные проверки перед коммитом;
- дополнительные файлы, запрещённые к коммиту.

Агенты читают `CLAUDE.md` и `AGENTS.md` автоматически и считают их правила приоритетными — поэтому
устаревшее правило в этом файле отравляет все последующие ревью. Собрать файл помогает
`/context-init`, сверить с реальностью — `/context-refresh`; расхождения, замеченные по ходу
ревью, попадают отдельной строкой в итог отчёта.

Ключевая развилка при обновлении решается не автоматически: расхождение файла с кодом означает
либо что правило устарело, либо что код нарушает живое правило. В первом случае правится файл,
во втором — код. Молча «обновив» файл под сломанный код, легко узаконить дефект.

## Разработка

Правки в файлах плагина видны без переустановки — может понадобиться перезапуск сессии.
Локальная установка читает файлы напрямую.

**Поднимай версию в `plugins/<имя>/.claude-plugin/plugin.json` при каждом изменении плагина.**
У тех, кто ставил с GitHub, `/plugin update <имя>` ориентируется на версию: без её повышения
изменения не подхватятся. Что менялось — в [CHANGELOG](CHANGELOG.md).

После изменений закоммить и запушить: репозиторий и есть источник правды.
