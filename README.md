# claude-plugins

Личный каталог плагинов Claude Code и Codex. Для Codex полностью адаптирован **review-kit**;
остальные плагины пока работают в Claude Code.

**[Памятка](CHEATSHEET.md)** — что набирать и когда. **[Изменения](CHANGELOG.md)** — что менялось.
Ниже — как это устроено.

| Плагин | Назначение |
|---|---|
| **review-kit** | Ревью-агенты с чек-листами под стек проекта |
| **tooling-kit** | Находит, как в проекте реально запускаются тесты и линтеры: `/test`, `/lint`, `/typecheck`, `/fmt` |
| **context-kit** | Создаёт и поддерживает `CLAUDE.md`: `/context-init`, `/context-refresh` |
| **debug-kit** | Разбор бага от симптома до причины через историю репозитория: `/debug` |
| **upgrade-kit** | Инвентаризация зависимостей и план обновления: `/upgrade-check` |
| **git-kit** | Где HEAD и что подвисло, когда git-интерфейса нет: `/git-state` |
| **explain-kit** | Пересказ технического отчёта по-человечески, с вариантами решения: `/explain` |
| **workflow-gate** | Ворота на фан-аут агентов: каждый запуск решает судья, продавить — `/workflow-pass` |

review-kit использует tooling-kit, если тот установлен: агенты берут команды у него, а не угадывают.

Общий набор ревью-агентов и команд для всех проектов. Ставится один раз, работает везде —
копировать `.claude/` из проекта в проект больше не нужно.

Чек-листы разделены на три слоя: универсальный (в агентах), стековый (картриджи `stack-*`)
и доменный (остаётся в `CLAUDE.md` конкретного проекта).

## Установка в Claude Code

```bash
/plugin marketplace add darkezar/claude-plugins
/plugin install review-kit@darkezar
```

Каталог добавляется один раз — дальше из него ставится что угодно. Плагины независимы,
весь набор брать необязательно:

```bash
/plugin install workflow-gate@darkezar
```

Команды на установку всех восьми — в [памятке](CHEATSHEET.md#установка-на-новой-машине).
Управление — `/plugin`: список, включение и выключение, обновление.

`workflow-gate` дополнительно требует `python3` в `PATH` и команду `claude`: хук зовёт её
как судью. Остальным плагинам не нужно ничего, кроме самого Claude Code.

Правка каталога у себя — в разделе [Разработка](#разработка): там подключение путём вместо
имени и порядок доставки изменений.

## Установка в Codex

Нужен актуальный Codex с командами `codex plugin`. Для GitHub PR также нужны `git`,
авторизованный GitHub CLI (`gh auth login`) и `python3` для локального журнала прогонов.
Claude Code и отдельный MCP-сервер для этой версии не нужны.

В терминале один раз добавь каталог и установи плагин:

```bash
codex plugin marketplace add darkezar/claude-plugins
codex plugin add review-kit@darkezar
```

Открой новый чат Codex в нужном проекте. Если список навыков не обновился, перезапусти клиент.
Плагин доступен в разделе Plugins; в CLI можно открыть `/plugins`.

Примеры сообщений в Codex:

```text
$review-kit:agent-full-review Проверь текущую ветку
$review-kit:agent-full-review 14343
$review-kit:agent-full-review https://github.com/owner/repo/pull/14343 security,auth
$review-kit:agent-full-review 14343 --comment
$review-kit:agent-full-review 14343 --fix
$review-kit:agent-full-review 14343 --no-pr-log
$review-kit:pr-comments Опубликуй готовый отчёт в PR 14343
$review-kit:apply-fixes Исправь все замечания последнего ревью
$review-kit:review Быстро проверь текущие изменения
$review-kit:ship Отправь изменения и создай или обнови PR
$review-kit:security-review 14343
$review-kit:design-review Проверь изменения UI
$review-kit:i18n-sync --check
$review-kit:i18n-sync Синхронизируй недостающие ключи
```

Навыки Codex имеют пространство имён `review-kit:`. Их можно выбрать через селектор навыков
из Review Kit. Можно также написать обычным текстом:
«Проверь PR 14343 с помощью Review Kit».

Полный набор Review Kit в Codex — **18 навыков**, включая обе команды Claude Code:

| Навык (после `$review-kit:`) | Назначение |
|---|---|
| `agent-full-review` | Полное ревью с выбором зон, повторными прогонами и журналом PR |
| `review` | Быстрое ревью одним проходом, без подагентов и кэша полного ревью |
| `branch-review` | Корректность, типы, архитектура, ошибки и тесты |
| `security-review` | Секреты, инъекции, внешние границы доверия и утечки |
| `auth-review` | Аутентификация, права, IDOR и жизненный цикл токенов |
| `performance-review` | Запросы, кэш, списки, рендеры и бандл |
| `design-review` | Токены, UI-примитивы, темы и локализация |
| `simplify-review` | Дублирование, лишняя сложность и возможности переиспользования |
| `apply-fixes` | Все готовые замечания, включая предложения; ответы в PR и resolve решённых обсуждений |
| `pr-comments` | Публикация всех замечаний: важное inline, остальное блоком suggestion |
| `ship` | Отдельная ветка → проверки → commit → push → новый или существующий PR |
| `i18n-sync` | Проверка словарей и механическая синхронизация без придуманных переводов |
| `detect-stack` | Фактическая база PR/ветки и стеки приложений |
| `stack-laravel`, `stack-yii2`, `stack-nextjs`, `stack-react-spa`, `stack-expo-rn` | Пять общих картриджей стека |

В Codex вызывай `$review-kit:ship` или выбирай Ship в селекторе навыков.
Слэш-форма `/review-kit:ship` относится к интерфейсу команд Claude Code.

Codex выбирает те же шесть зон и читает те же чек-листы в `agents/` и `skills/stack-*`.
Если делегация доступна и разрешена окружением, зоны проверяются подагентами; иначе —
последовательными проходами. Claude-специфичные Agent tool и `workflow-gate`
в Codex не используются. Состав запроса `agent-full-review` можно задать как `all`, `min`
или `security,auth`. Быстрое и точечные ревью выполняются одним проходом;
они не используют кэш и не пишут журнал полного ревью.

Модель и effort выбираются по сложности и риску в обоих клиентах; минимумы, fallback
и ограничения клиентов — в [политике исполнения](plugins/review-kit/references/execution-routing.md).
`max` включается по необходимости, глобальные настройки пользователя не переписываются.

Ревью PR привязано к его фактическим base/head SHA. Для другой головы или грязного дерева
создаётся отдельный detached worktree; текущая ветка и правки пользователя сохраняются.
Код проверяется без автофиксов. Исправления запускаются с `--fix`, все замечания публикуются
с `--comment` или через `pr-comments`: важное inline, механическое, мелкое и необязательное —
текстовым блоком `suggestion` в body review. Отложенные предложения тоже передаются;
счётчик не заменяет содержание. Важное без допустимой строки сохраняется в «Важное вне диффа».
Повторный запуск учитывает и inline, и body прежних reviews; перед и после отправки проверяется
покрытие всего отчёта. Отправка review в GitHub идёт
от аккаунта `gh`, тип review — `COMMENT`.

Журнал Codex локальный: `$(git rev-parse --git-common-dir)/review-kit-codex.jsonl`.
В нём обе стороны сравнения, отпечатки дерева, правил и чек-листов пакета. Rebase, смена
базовой ветки, изменение правил или чек-листов требуют полного прогона. Продвижение базы PR
и вливание базы в ветку учитываются отдельно от своих коммитов и разрешённых конфликтов:
проверяется влияние на PR, включая уже проверенные неизменённые файлы. Совпавший снимок
позволяет переиспользовать анализ кода. На другой машине без журнала выполняется первое ревью.

В Claude и Codex `agent-full-review` перед решением о мерже обновляет CI, показывает компактную
таблицу безопасности с доказательствами (`проверено / находка / не проверено / неприменимо`)
и выводит `МЕРЖИТЬ / МЕРЖИТЬ ПОСЛЕ <условие> / НЕ МЕРЖИТЬ` отдельно от вердикта по коду.
Ожидание CI выполняет скрипт с ограниченным бюджетом, без вызова модели на каждый опрос;
недоступный, незавершённый или устаревший CI не считается успешным. Автоисправления CI —
только по запросу исправлений, до трёх попыток, с остановкой без новых подтверждений.
На повторных кругах проверяются прирост, открытые замечания и затронутые старые потребители.
Третий круг с повторяющейся ошибкой требует проверки первопричины, а не всех агентов по
привычке. Тяжёлые тесты, Docker, пробное слияние базы и соседние репозитории — только при
обоснованном риске и доступной проектной среде. Проверки не дублируются, логи сводятся,
полный список находок сохраняется. Одно обновление CI не увеличивает круг анализа.
Подробности — в [общей политике полного ревью](plugins/review-kit/references/balanced-review.md).

Если PR существует, каждый завершённый прогон `agent-full-review` также записывается в один комментарий-журнал
с общим для Claude и Codex маркером `review-kit:log`. В нём указаны проверенные head/base SHA,
время, состав, режим и вердикт. Ревью незакоммиченных изменений в журнал PR не пишется: оно
проверяет не коммит. `--comment` для этой записи не нужен; `--no-pr-log` отключает
только журнал в PR. Повторение прежнего результата не добавляет дубликат, а пропущенная запись
может быть восстановлена из локального журнала. Если запись невозможна, агент сообщает причину.

Вызов `ship` разрешает commit, push и создание/обновление PR в рамках задачи, без повторного
подтверждения уже заданной команды. Он сохраняет несвязанные правки и индекс пользователя,
не коммитит в базовую ветку, не использует force-push и обновляет существующий PR той же ветки.
Проверки берутся из проекта; `tooling-kit` и Claude Code не обязательны. Проверка дизайна
и `i18n-sync --check` не меняют словари; синхронизация добавляет заглушки основной локали
и перечисляет требующие перевода ключи.

Обновление каталога и установленного пакета:

```bash
codex plugin marketplace upgrade darkezar
codex plugin add review-kit@darkezar
```

После обновления начни новый чат. Для проверки ветки до её слияния в `main` добавляй каталог
с `--ref <ветка>`. Для локальной разработки вместо GitHub можно указать путь к этому репозиторию.

Review Kit перенесён полностью. Остальные плагины каталога (`tooling-kit`, `context-kit`,
`debug-kit`, `git-kit`, `upgrade-kit`, `explain-kit`, `workflow-gate`) пока предназначены
для Claude Code и не устанавливаются как часть Review Kit.

## Что набирать

Далее приведены команды **Claude Code**. Соответствия для Codex — в разделе выше.

### Основное

| Команда | Что делает |
|---|---|
| **`/agent-full-review`** | **Главное.** Выбирает зоны по риску, повторно проверяет прирост и затронутые старые файлы. Обновляет CI, показывает покрытие безопасности и условия мержа. Тяжёлые проверки — по необходимости |
| `/ship` | Ветка → проверки → коммит → push → Pull Request |
| `/test` · `/lint` · `/typecheck` · `/fmt` | Из **tooling-kit**: запускают то, что реально настроено в проекте |

Аргументы к первой: `all` — все шестеро принудительно, `min` — только код-ревью,
`security,auth` — ровно перечисленные, `--fix` — применить все замечания после отчёта,
`--comment` — выложить все замечания в PR: важное inline, остальные блоком `suggestion`;
номер или ссылка PR — ревьюить ветку этого PR.

### Точечно, когда нужен один ревьюер

`/security-review` · `/auth-review` · `/performance-review` · `/design-review` ·
`/simplify-review` · `/branch-review`

### Остальное

| Команда | Что делает |
|---|---|
| `/review` | Ревью одним проходом, без агентов — быстро и дёшево, но поверхностнее |
| `/apply-fixes` | Исправить все готовые замечания, включая предложения; ответить на inline и закрыть решённые обсуждения PR |
| `/pr-comments` | Выложить весь отчёт ревью в PR: важное inline, механическое и мелкое блоком suggestion в body, с проверкой полноты и без дублей |
| `/i18n-sync` | Сверка и починка словарей локализации |
| `/git-state` | Из **git-kit**: где ты сейчас, что не закоммичено, что забыто в ветках и стешах |
| `/explain` | Из **explain-kit**: пересказать отчёт коротко и без жаргона — что не так, почему это плохо, что можно сделать |
| `/workflow-pass` | Из **workflow-gate**: временно пустить фан-аут в обход судьи, на заданное число часов |
| `/debug` | Из **debug-kit**: симптом → воспроизведение → причина, с разбором по истории |
| `/upgrade-check` | Из **upgrade-kit**: что отстало, что без поддержки, план по шагам |
| `/context-init` · `/context-refresh` | Из **context-kit**: собрать `CLAUDE.md` · сверить его с реальностью |
| `/detect-stack` · `/detect-tooling` | Служебные: базовая ветка и стек · точки входа тулинга |

**Починка.** Ревьюеры read-only — у них нет `Edit`/`Write`, и это намеренно: правящий ревьюер
оценивает собственную работу, а шесть параллельных писателей конфликтуют в одном дереве.
Правки применяет отдельный `agent-fixer` после отчёта, последовательно.

В Claude и Codex `apply-fixes`/`--fix` применяет весь готовый отчёт, включая предложения.
Вопрос нужен только при существенной неоднозначности; детали и исключения — в
[общей политике исправлений](plugins/review-kit/references/fix-scope.md).

Запуск: `/agent-full-review --fix` или `/apply-fixes`.

В Claude и Codex `apply-fixes` отвечает на **каждый inline-комментарий PR, по которому
внесена правка**: что изменено, чем проверено, известный коммит. Целиком решённые обсуждения
закрываются через resolve после подтверждения исправления в опубликованном коде PR.
Локальные/частичные исправления получают честный ответ и остаются открытыми; после
разрешённого `ship` обработка ожидающих обсуждений продолжается. Повторный запуск не
дублирует ответы. `--comment` для этих ответов не нужен; явный запрет GitHub-действий
сохраняется. Нет доступа/прав — подготовленные ответы и причины остаются в локальном отчёте.

**Агенты** — по одному на роль: `agent-branch-reviewer`, `agent-security-reviewer`,
`agent-simplify`, `agent-design-reviewer`, `agent-performance-reviewer`, `agent-auth-reviewer`.

## Как это работает

`agent-full-review` определяет базовую ветку (`main`, `master`, `develop` — по remote, а не
хардкодом), детектит стек по файлам-маркерам, **решает, какие ревьюеры вообще нужны**, и
запускает только их — параллельно.

Фиксированного набора нет: ни один агент не включается автоматически. Оркестратор сначала
классифицирует дифф (характер правки, затронутые слои, пересекается ли граница доверия, объём),
затем по каждому агенту принимает решение и обосновывает его одной строкой в отчёте. Ревью
одного PHP-класса не потянет за собой дизайн-ревьюера, а правка цвета кнопки — проверку индексов.

Запас несимметричен: **security** и **auth** включаются по слабому признаку (пропущенная дыра
дороже лишнего прогона), **design** и **performance** — только по явному, **simplify** — по
объёму диффа. На тривиальной правке фан-аут не разворачивается вовсе.

Аргументы: `all` / `full` — все шестеро; `min` / `core` — только код-ревью; `security,auth` —
ровно перечисленные.

### Разведённые зоны

Каждый агент отвечает за свою тему и не лезет в чужую, иначе одно замечание приезжало бы в отчёт
по четыре раза.

| Зона | Агент |
|---|---|
| Типы, паттерны, архитектура, тесты | branch |
| Уязвимости, секреты, инъекции | security |
| Права, сессии, токены, IDOR | auth |
| Ре-рендеры, списки, N+1, индексы, бандл | performance |
| Токены темы, примитивы, локализация | design |
| Дублирование, сложность, мёртвый код | simplify |

Если агент не запускался ради экономии, его зону **добирает** ближайший из запущенных — по верхам,
с пометкой добора (`auth` → `security` → `branch`). Если же агент пропущен потому, что его темы
в диффе просто нет, добор не назначается: покрывать нечего. Поэтому оркестратор передаёт каждому
агенту состав прогона и причину пропуска.

### Картриджи стека

Картридж — это три таблицы для конкретного стека: команды тулинга, триггеры условных ревьюеров
и привязки универсального чек-листа к API этого фреймворка.

Готовы: `stack-laravel`, `stack-yii2`, `stack-nextjs`, `stack-react-spa`, `stack-expo-rn`.

Стеков может быть активно несколько одновременно — в монорепо обычно фронт плюс бэк.

### Сортировка по риску потери

`/git-state` устроен вокруг одного вопроса: **что исчезнет, если этот диск умрёт прямо сейчас.**

Привычная группировка — отдельно ветки, отдельно стеши, отдельно `git status` — сваливает в одну
кучу вещи с несопоставимой ценой. Поэтому находки делятся иначе:

| Уровень | Что сюда попадает |
|---|---|
| **Только здесь** | незакоммиченное и неотслеживаемое, коммиты на ветках без upstream, стеши, worktree, detached HEAD |
| **Мешает** | незапушенное с upstream, отставание от базы, застрявший rebase или merge |
| **Мусор** | слитые ветки, `[gone]` upstream, стеши, уже вошедшие в базу |

Отсюда же главное ограничение: команда, которая существует ради сохранности работы, не имеет
права её терять. `git reset --hard`, `git clean`, `git stash drop`, `git branch -D` и
`push --force` она по своей инициативе не выполняет никогда, а `git branch -d` использует
именно в строчной форме — её отказ удалять неслитую ветку и есть страховка.

**Добавить новый плагин:** создай `plugins/<имя>/` с тем же устройством и допиши его в
`.claude-plugin/marketplace.json`. Плагины ставятся и выключаются независимо.

**Добавить новый стек:** создай `plugins/review-kit/skills/stack-<имя>/SKILL.md` по образцу
существующего и допиши строку в таблицу детекта в `skills/detect-stack/SKILL.md`. Агентов
трогать не нужно.

## Что остаётся в проекте

В `CLAUDE.md` каждого проекта — то, что не выводится из стека:

- доменные инварианты («сервер — единственный авторитет по деньгам», «дверь открывает только сервер»);
- локальные конвенции и запреты;
- префикс веток, если он отличается от `darkezar/`;
- дополнительные проверки перед коммитом;
- дополнительные файлы, запрещённые к коммиту.

Агенты читают `CLAUDE.md` и `AGENTS.md` автоматически и считают их правила приоритетными — поэтому
устаревшее правило в этом файле отравляет все последующие ревью. Собрать файл помогает
`/context-init`, сверить с реальностью — `/context-refresh`; расхождения, замеченные по ходу
ревью, попадают отдельной строкой в итог отчёта.

Ключевая развилка при обновлении решается не автоматически: расхождение файла с кодом означает
либо что правило устарело, либо что код нарушает живое правило. В первом случае правится файл,
во втором — код. Молча «обновив» файл под сломанный код, легко узаконить дефект.

## Разработка

### Codex

Нативный каталог Codex — `.agents/plugins/marketplace.json`. Он ссылается на тот же
`plugins/review-kit`, что каталог Claude; Codex читает `.codex-plugin/plugin.json` и
навыки из `codex-skills/`, Claude Code — `.claude-plugin/plugin.json` и `skills/`.
Содержимое `agents/` и картриджей стека общее и поставляется внутри пакета: внешних ссылок
на checkout автора нет. Версии двух манифестов review-kit должны совпадать.

Локальная проверка устанавливаемого пакета:

```bash
codex plugin marketplace add /absolute/path/to/claude-plugins
codex plugin add review-kit@darkezar
codex plugin list --json
python3 -m unittest discover -s tests -v
```

После изменения файлов повтори установку и открой новый чат: Codex использует установленную
копию пакета. Правила кэша Claude из следующего раздела не следует переносить на Codex.
Синтаксис установки сверяется с [документацией OpenAI](https://developers.openai.com/plugins/build/plugins).
Проверка через `skills/list` app-server должна показывать все 18 навыков Review Kit
из установленного `codex-skills/`, без ошибок. Чек-листы из `skills/` и `agents/` остаются
справочниками, а не дополнительными Claude-обёртками. Тест `test_codex_package.py`
сравнивает инвентарь Codex с объединением `commands/` и `skills/` Claude и проверяет,
что все ссылки разрешаются внутри устанавливаемого пакета.

### Claude Code

Свой экземпляр каталога подключается путём вместо имени:

```bash
/plugin marketplace add /путь/к/claude-plugins
```

Правки в файлах плагина видны без переустановки — может понадобиться перезапуск сессии.
Локальная установка читает файлы напрямую.

**Поднимай версию в `plugins/<имя>/.claude-plugin/plugin.json` при каждом изменении плагина.**
У тех, кто ставил с GitHub, `/plugin update <имя>` ориентируется на версию: без её повышения
изменения не подхватятся. Что менялось — в [CHANGELOG](CHANGELOG.md).

После изменений закоммить и запушить: репозиторий и есть источник правды.

### Кэш врёт при локальной отладке

`~/.claude/plugins/cache/<каталог>/<плагин>/<версия>/` — снимок на момент установки. Каталог,
подключённый как `directory`, грузится мимо него, поэтому кэш спокойно расходится с рабочим
деревом и живёт со старой версией в имени папки. Проверять, что именно подхватилось, надо по
рабочему дереву; кэш в этой схеме не показатель ничего.

Видно в `~/.claude/plugins/known_marketplaces.json`: у каталога с `source: directory` поле
`installLocation` указывает на сам репозиторий, а не на копию. Отсюда и следствие — версию
для своей копии поднимать не нужно, а `/plugin update` отвечает «already at the latest
version» независимо от того, что в файлах.

### Ключ инструментов различается у агента и у команды

| Файл | Ключ | Формат |
|---|---|---|
| `agents/*.md` | `tools` | массив: `tools: ["Read", "Grep", "Bash"]` |
| `commands/*.md`, `skills/*/SKILL.md` | `allowed-tools` | список, допускает скоупы: `Bash(git diff)` |

Перепутать легко, а **ошибка молчит**: `allowed-tools` в файле агента просто игнорируется, и
агент получает не заявленный набор, а **все инструменты сразу** — ровно противоположное тому,
что написано в его фронтматтере. Ни ошибки, ни предупреждения при этом не будет.

Плата за правильный ключ: `tools` принимает только имена, без скоупов. Сузить агента до
`Bash(git diff)` через фронтматтер нельзя — либо `Bash` целиком, либо ничего. Если нужен
именно узкий шелл, это делается снаружи, разрешениями в `settings.json`, а не в плагине.
